## 1. 产品理解：印证该扮演什么角色

```text
帖子内容（真实）
    │
    ├─ 与用户偏好 / 机酒围栏 / 天数 重合的部分  →  可借鉴为玩法节点（或 tips）
    ├─ 不重合、互斥、过远、过密的部分          →  丢弃或降为次选 / 分日
    └─ 价格 / 营业时间 / 「必须照抄整篇」       →  一律不采信
```

| 层（见 [19](./19-玩法印证与UGC数据源分析.md)） | 印证能帮什么 | 印证不能替代 |
|-----------------------------------------------|--------------|--------------|
| L-pattern（怎么排日子） | 高 | — |
| L-geo（点在哪） | 弱（抽名后仍要 geocode） | 封闭地图 POI 池 |
| L-fact（开放/预约） | 弱 | 官方/Places |
| L-price | ❌ | 机酒/深链 |

**一句话**：印证是 **L-pattern 参考源**，应经「过滤 → 重合判断 → 部分采纳」再进节点；不是第二套行程生成器。

## 2. 整体流程步骤（现状 · 端到端）

### 2.1 总览（机酒 → 印证 → 玩法）

```text
① 对话 / 表单
      ↓ 目的地 · 日期 · 人数 · 偏好 ·（可选）规划策略
② 确认航班（硬门禁）
      ↓ travel_intel.flights[]
③ 住宿：片区推荐（可选）→ 锁定具体酒店名+坐标（硬门禁）
      ↓ travel_intel.hotels[] 含 lat/lng
④ 玩法印证（软，可空）
      ├─ 用户贴链检索（可选，面板内主动点「检索」）
      └─ 生成时自动 EvidencePack（TikHub 小红书 + 可选 Tavily）
⑤ 生成玩法 generate / regenerate
      ↓ 合并证据 → 抽 POI →（可选）CLOSED_POI_POOL 注入
      ↓ 单次 LLM 精排（HARD 机酒 > 用户笔记 > 偏好 > 自动帖）
⑥ 后处理
      ↓ geocode 围栏 · 机酒锚 enforce · 停留夹逼 · 可信度 warning
⑦ 地图 / 总览编辑；改机酒 → dirty → optimize / regenerate
```

**硬阻断**：无航班、无锁店 → 不能首次 generate / regenerate。  
**印证为空**：仍可生成（checklist 软项）；自动检索失败 soft-fail，不挡主路径。

### 2.2 印证子系统 · 两条入口

#### A. 用户贴链（[23](./23-玩法印证贴链MVP实施.md) · 生成前可见）

```text
EvidencePanel
  → 粘贴 URL（可多条，独立卡片）
  → 用户点「检索」
  → POST /api/v1/ugc/evidence/from-link
  → Provider（MVP：小红书 TikHub；失败可 Tavily 抽正文）
  → 卡内展示 title / snippet / likes（及 poi_hits 若有）
  → 【产品约定 · 待做】检索成功后：勾选「采纳哪些地点/片段」
        （采纳发生在印证步、按帖完成；不是生成前一次性总勾）
  → generate 仅注入：status=ok 且已勾选采纳的内容 / adopted POI
```

- **现状不做**：卡内采纳勾选、卡内 LLM「玩法分析」、粘贴后自动批量检索（23 §9 曾列「人勾选采纳」为后续）。
- **产品已拍板（2026-08-11）**：人确认采纳 **就在玩法印证**；**单帖检索完成后即可操作**，见 §5。

#### B. 自动印证包（生成时）

```text
generate 开始
  → _finalize_evidence_for_generate
  → fetch_evidence_pack（TikHub 按目的地/天数搜笔记 + 可选 Tavily）
  → filter_evidence_items（去广告、错城、域名/条数上限）
  → 与 user_evidence 合并（用户帖在前）
  → enrich_evidence_pois：
        标题/摘要抽地名 → 目的地围栏内 geocode
        → verified / lat/lng / poi_hits
        → 可选 Places 类型/评分 soft enrich
  → 注入 prompt + 写入 itinerary.meta.evidence / poi_candidates
```

### 2.3 注入与权重（进入 LLM 前）

```text
HARD CONSTRAINTS（确认航班/酒店时刻与锚点）
  > USER_SELECTED_UGC（用户已检索贴链）
  > USER_DATA（preference_tags / free_text / notes）
  > UNTRUSTED_UGC（自动检索公开帖）
```

Prompt 已写明的「部分借鉴」意图：

- 多条用户笔记冲突 → **优先共同提及**；其余分日或次选；禁止同日硬塞互斥行程。  
- 自动检索 **不得覆盖** 用户指定笔记的玩法取舍。  
- 与 HARD 冲突以 HARD 为准；**价格/营业时间不以笔记为准**。  
- 若有 `CLOSED_POI_POOL`（verified 候选名）：attraction/landmark **须选自池**（仍主要靠模型遵守，生成后无出池硬拒）。

### 2.4 生成后（与印证的关系）

| 步骤 | 是否用印证结果 |
|------|----------------|
| geocode 节点 | 否（按节点名+机酒锚围栏） |
| enforce 机酒日闭环 | 否 |
| `meta.evidence` 展示「参考依据」 | 是（列表级，非节点级引用） |
| 节点标记「来自哪条笔记」 | ✅（`evidence_refs`；仅已采纳帖） |
| 代码检查：节点是否出自印证/池 | **否**（仅有 prompt HARD） |

## 3. 「先判断再部分借鉴」核对表

| 期望步骤 | 现状 | 判定 |
|----------|------|------|
| 拉取真实帖子（小红书等） | TikHub + 贴链；过滤广告/错城 | ✅ 有 |
| 识别帖内地点 | 正则/启发式抽名 + geocode 核验 | ✅ 弱有 |
| 与用户想玩 / 机酒围栏算重合 | 无独立评分；围栏只服务 verified 标记 | ⚠️ 缺 |
| 只把重合部分写成节点候选 | 整段摘要进 prompt，由 LLM 自选 | ⚠️ 软 |
| 人确认「采纳哪些」 | ✅ 印证面板单帖检索后勾选（`EvidencePanel` + `evidenceAdopt.ts`） | ✅ |
| 节点可追溯出处 | 未做 | ❌ |
| 池外/未核验禁止进 attraction | prompt 有；代码无拒收 | ⚠️ 半 |

**结论**：设计文档与 prompt **承认**「部分重合、冲突取交集」；工程上 **没有**把「判断」做成可测管道，因此「借鉴」质量完全取决于单次 generate 的模型行为。

## 4. 与「玩法难落地」的关系

```text
印证帖真实
    ≠ 行程可落地

缺口叠加：
  1. 印证 → 节点：无强制部分采纳（本文）
  2. 玩法候选：非地图封闭池，偏 LLM 起名（[24] 主缺口）
  3. ACT-POOL：依赖印证抽名 verified；池空则约束消失
  4. 规划策略三档：不改变机酒门禁，几乎不改变印证管道
```

因此：加强印证「部分借鉴」**有助于**节奏与可解释性，但若不同时做 **围栏内真实 POI 池 + 出池执法**，地图落点与「像不像当地能玩」仍会飘。

## 5. 建议的目标态（对齐产品理解 · 部分已拍板）

### 5.1 贴链卡内采纳（HITL 落点）

```text
EvidencePanel 单卡
  → 用户点「检索」→ status=ok + 展示正文/摘要
  → （可选）抽 POI / poi_hits 展示为可勾选项
  → 用户勾选「采纳这些地点 / 采纳此帖节奏参考」
  → 模块持久化 adopted_pois[] / adopt_post: bool（进 TravelPlan）
  → generate：
        USER_SELECTED_UGC 优先用「已采纳」切片（非整篇硬塞）
        adopted 地点进入玩法候选（再与围栏/封闭池求交）
```

| 原则 | 说明 |
|------|------|
| **时机** | 印证步、**按帖**；检索完就能勾，可改勾后再生成 |
| **粒度** | 优先「地点级」勾选；整帖「仅作节奏参考」可为辅开关 |
| **未勾选** | 该帖可仍展示在面板，但 **不进** generate 的强权重注入（或降为忽略） |
| **自动检索包** | 生成时 auto UGC 仍可作弱补齐；**不**要求人在生成瞬间勾自动帖（避免打断）；有贴链采纳时以采纳为准 |

### 5.2 与封闭池衔接

```text
帖子 / 贴链检索
  → 卡内勾选 adopted（§5.1）
  → 与「酒店围栏 ∩ 地图/Places 封闭池 ∩ 用户偏好」求交   ← 「判断」
  → generate：LLM 主要从 adopted ∪ 封闭池排序编排
  → 节点写入 evidence_refs[]
  → 代码：attraction 不在池内 → warning 或打回
```

| 优先级 | 项 | 说明 |
|--------|-----|------|
| **P1（已拍板 UX）** | ✅ 印证面板：单帖检索后勾选采纳地点/片段 | `EvidenceLinkModule.adoptedPois` / `adoptRhythm`；generate 只吃已采纳 |
| **P0** | ✅ 封闭 POI 池（地图 API）+ 出池代码执法 | `closed_poi_pool.py`：Maps 补池（种子不足时）· adopted∩围栏 · `enforce_closed_poi_pool` |
| P1 | 印证 adopted ∩ 围栏 → 候选进 prompt | ✅ `promote_adopted_candidates` + merge；围栏外不标 verified |
| P1 | 节点 `evidence_refs` + 卡片展示 | ✅ `evidence_borrow.attach_evidence_refs` · TripNode「印证」链 |
| P1 | L3 must / nice | ✅ `adoptLevels` · prompt + 缺必去 warning · 命中取消 optional |
| P2 | 生成前可预览自动印证 | **未做** |
| — | L8 有采纳时跳过 auto 包 | ✅ `_merge_user_and_auto_evidence` |
| — | U8 checklist 以采纳为准 | ✅ `planReadiness` |
| — | L12 已检索未采纳软警告 | ✅ |

## 6. 文档尚未覆盖的优化点（复核 · 2026-08-11）

> 相对 §0–§5 已写内容的 **增量缺口**。分 **用户体验** / **逻辑管道**；实施前需再排优先级，不默认全部做。

### 6.1 用户体验（印证面板 / 流程感知）

| # | 缺口 | 为何重要 | 建议方向 |
|---|------|----------|----------|
| U1 | **默认勾选策略未定** | 检索后若全空勾，用户易漏；若默认全选，又回到「整篇进模型」 | 默认勾 **已定位/围栏内** POI；围栏外默认不勾并灰显原因 |
| U2 | **抽不出地点时怎么采纳** | 很多帖只有「节奏/避坑」无干净店名；仅地点勾选会空 | 保留「整帖作节奏参考」开关；允许 **手补地点名** 再勾选 |
| U3 | **围栏外/错城 POI 仍可勾** | 用户不知点已漂到别国 | 卡内标注「距酒店过远 / 未过围栏」；可勾但强警告，或禁止勾 |
| U4 | **先贴链后锁店 / 换店换目的地** | 采纳时还没有酒店围栏；锁店后旧采纳可能失效 | 锁店或改 destination 后 **重校验 adopted**；失效项取消勾并 toast |
| U5 | **多帖勾到同一地点** | 重复进池、权重不清 | 合并为一条候选，展示「来自 N 帖」；冲突文案仍可保留 |
| U6 | **采纳过多** | 5 日行程勾 20+ 必去 → 必过满或被模型丢弃，用户感觉「勾了没用」 | 按 `day_count` 软上限（如每天 2–3 景点）；超限提示「请精简或接受分日次选」 |
| U7 | **印证入口时机弱** | 文档写在机酒后，UI 仍随时可开；易在无目的地时贴链失败 | 无 destination 时禁用检索并说明；锁店后摘要/下一步轻推「可贴攻略勾地点」 |
| U8 | **checklist「印证」完成条件** | 现仅 `status=ok` 条数；有采纳后应区分「已检索」vs「已采纳」 | `done` = 至少 1 个 adopted，或显式「跳过印证」 |
| U9 | **生成后再贴链** | 只能 dirty 机酒才 optimize；加了采纳无法「按新印证重排」 | 采纳变更也标 soft-dirty / 提供「按已采纳印证优化」 |
| U10 | **失败与重试话术** | 402/短链/地区限制时卡内错误偏技术 | 固定文案 + 一键重试；短链提示「打开 App 复制最终链接」 |
| U11 | **重复 URL / 改 URL** | 改链接后旧采纳残留 | 改 URL 或重新检索 → 清空该卡 adopted，需重勾 |
| U12 | **隐私与预期** | 正文会进 LLM；赞藏数易被当成「官方推荐」 | 面板一句：「仅作参考·将送模型编排；赞数≠必去」 |

### 6.2 逻辑管道（判断 / 生成 / 一致性）

| # | 缺口 | 为何重要 | 建议方向 |
|---|------|----------|----------|
| L1 | **「节奏参考」如何进模型** | 只传 adopted 店名会丢「上午 A 下午 B」结构 | 采纳节奏时注入 **截断摘要 + 日序提示**；不采纳节奏则只传 POI 列表 |
| L2 | **adopted ∩ 封闭池失败** | 用户勾了但 Places/geocode 对不上正式名 | 展示「未匹配正式 POI」；允许保留为 soft must_see 或要求改名 |
| L3 | **必去 vs 可选** | 现设计只有勾/不勾 | ✅ `adoptLevels` must/nice；缺 must → warning |
| L4 | **品类混勾** | 餐饮/景点/交通点同一列表 | 勾选时带 category；餐饮走价位带规则，不进 CLOSED_POI_POOL 景点硬池 |
| L5 | **与主题 Tag / 偏好不同步** | [33](./33-提示词主题Tag分析.md) 主题与印证两套 | 采纳 POI 可反推/补强 preference；或生成时两边一并注入 |
| L6 | **activity_first 与采纳** | C 档要骨架；仅贴链未勾选是否算骨架？ | 约定：C 档硬门禁改为「≥1 adopted 或足够 notes」；仅 ok 未勾不够 |
| L7 | **optimize 是否尊重新采纳** | optimize 倾向保留旧节点名 | 印证采纳变更时默认 **regenerate** 或 optimize 提示「将尽量插入已采纳点」 |
| L8 | **自动包与采纳抢权** | 已有 adopted 时 auto UGC 仍可能带进冲突店 | 有 adopted 时 **缩小或关闭** auto 景点名注入，只留 tips 级 |
| L9 | **抽名质量** | 昵称店、英文混写、列表「①②③」漏抽 | 检索后服务端加强抽取；卡内支持手补（接 U2） |
| L10 | **地理聚类** | 采纳点分属两城/两岸 | 生成前聚类 warning：「已采纳点跨区，建议改酒店或取消部分」 |
| L11 | **evidence_refs 与未采纳** | 生成后 meta.evidence 仍可能列出未勾帖 | ✅ 节点 refs **只链 adopted**；meta 列表分栏仍可后续做 |
| L12 | **空采纳仍 status=ok** | 用户检索了但全不勾又生成 | 软警告「未采纳任何地点，将主要靠模型与自动印证」；不硬挡（除非 C 档） |

### 6.3 与 §5 的关系（避免范围膨胀）

```text
  默认勾谁 · 抽空怎么办 · 换店失效 · 勾太多 · checklist 语义
  节奏 vs 地点 · must/nice · 与 C 档/optimize/自动包一致
```
