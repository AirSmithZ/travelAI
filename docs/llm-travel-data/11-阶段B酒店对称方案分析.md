## 0. 结论摘要

| 维度 | 能否复用航班同样方式 | 说明 |
|------|---------------------|------|
| 左栏独立视图（与 Chat 分离） | ✅ **可以** | 扩展 `leftPanelMode: 'hotel'` 或 `intel` 内 Tab |
| 三态 badge（阶段 B / 待确认 / 已完成） | ✅ **可以** | `getHotelIntelPanelPhase` 对称 `getFlightIntelPanelPhase` |
| 确认后 CTA + 切 `form` | ✅ **可以** | 航班确认后「继续确认酒店」→ 切 `hotel` |
| 手动添加 + 已确认列表 + 移除同步 | ✅ **可以** | 对称 `FlightManualAddPanel` / `addManualHotelStay` |
| Trip.com 预订 deep link | ✅ **可以** | Phase 1 酒店主推路径（Affiliate） |
| Ignav 式 App 内 ranked 搜价 | ❌ **暂不能** | 无 `search_hotels` API；Ignav 仅航班 |
| stale-while-revalidate 搜索 | ⏳ **待 API** | 有 ranked 后可原样复制 `mergeHotelSearchResult` |
| 往返 bundle 一次确认 | ❌ **不适用** | 酒店按 **入住区间 × 城市** 分段，非往返组合 |
| `syncTravelIntelStatus` 现状 | ⚠️ **需扩展** | 当前只数 `flights.length`，忽略 `hotels[]` |

**产品建议**：酒店阶段 B **先用与航班相同的 UX 壳**，**Phase 1 能力 = 手动录入 + Trip.com CTA**；待 Partner/Places 就绪再挂 ranked 卡片，避免空壳搜索按钮。

## 1. 航班已落地的「同样方式」指什么

P3/P3.1 航班侧已固化的模式（[10-UX](./10-阶段B航班UX问题分析.md)、[09](./09-阶段B航班功能实施计划.md)）：

```
leftPanelMode: 'flight'（全高 Panel，无 Composer）
  ├─ badge：阶段 B → 待确认 → 已完成
  ├─ 搜索 ranked（Ignav）+ stale 保留旧结果
  ├─ 确认 → travel_intel.flights[] + hide_ranked + 切 form
  ├─ 手动添加（Trip 订好后补录）
  ├─ 移除航段 → syncFlightSearchAfterLegRemoval
  └─ 底栏 CTA：返回对话 · Trip.com · 继续编辑行程
```

数据层：

- `ConfirmedFlightLeg[]` + `FlightSearchSession`（`last_flight_search`）
- Store：`setFlightSearchResult` / `confirmFlightQuote` / `addManualFlightLeg` / `removeFlightLeg`

## 2. 酒店现状对照

### 2.1 已有

| 项 | 状态 | 路径 |
|----|------|------|
| `ConfirmedHotelStay` 类型 | ✅ 占位 | `travelIntel.ts`（无 quote/lat/address） |
| `travel_intel.hotels[]` | ✅ 空数组持久化 | `storage` v3 迁移 |
| 方案文档 Schema | ✅ | [06 §3.3](./06-机酒确认与行程生成流程方案.md)、[02 §3](./02-酒店信息.md) `HotelQuote` |
| generate 读 intel | ⏳ 未接酒店锚点 | P4 待做 |

### 2.2 缺失（相对航班）

| 项 | 航班 | 酒店 |
|----|------|------|
| 后端 search API | `POST /flights/search` + Ignav | ❌ 无 |
| 前端 Panel | `FlightIntelPanel` | ❌ 无 |
| SearchSession | `last_flight_search` | ❌ 无 `last_hotel_search` |
| Store 写入 | 4 个 action | ❌ 无 |
| 手动添加 UI | `FlightManualAddPanel` | ❌ 无 |
| leftPanelMode | `'flight'` | ❌ 无 `'hotel'` |
| 中文/别名解析 | `airportLabels.ts` | ⚠️ 可用 `DayPlan.region` / geocode，无专用表 |

### 2.3 数据源差异（决定能否复制「搜价卡片」）

| | 航班 | 酒店 |
|---|------|------|
| 已验证 App 内 API | Ignav Go（3/3 Spike） | 无对等物 |
| Phase 1 现实路径 | Ignav ranked + Trip 预订 | **Affiliate deep link** + LLM 区域推荐（[02 §4](./02-酒店信息.md)） |
| 商业 API | — | Partner API 2.0 / Apify 爬虫（非生产核心） |
| 产品决策 | 先做 Ignav | **Q3：航班跑通后再做酒店 API**（[06 §8](./06-机酒确认与行程生成流程方案.md)） |

因此：**不是「不想同样做」，而是「同样做 ranked 搜价」的前置 API 尚未存在。**

## 3. 可复用的 UX 架构（推荐）

### 3.1 方案 A（推荐）：`leftPanelMode: 'hotel'` 平行扩展

与航班对称，改动面清晰：

```typescript
type LeftPanelMode = 'chat' | 'flight' | 'hotel' | 'form';
```

```
┌─ hotel 模式 ──────────────────┐
│ HotelIntelPanel（100% 高度）   │
│ · 已确认入住段列表             │
│ · 搜索表单（Phase 1 可隐藏）   │
│ · 手动添加（P5a 主路径）       │
│ · ranked 卡片（P5b 后启用）    │
├─ 底栏 ────────────────────────┤
│ [返回对话] [Trip.com] [继续→]  │
└───────────────────────────────┘
```

**入口**：

- 对话栏 strip「酒店确认」（与「航班确认」并列）
- 航班确认完成 CTA：**继续确认酒店** → `setLeftPanelMode('hotel')`（[10-UX §1.3](./10-阶段B航班UX问题分析.md) 已预留）

### 3.2 方案 B：统一 `intel` 模式 + Tab

`leftPanelMode: 'intel'`，内 Tab `航班 | 酒店`。减少模式枚举，但 Panel 更重、与「搜完航班不想看对话」的单任务心智略冲突。**可作为 A 的后期合并**。

### 3.3 不建议

- 把酒店 Panel 塞回 `ChatPanel`（重复航班 P3 前的 38vh 问题）
- Phase 1 做「搜索酒店」按钮却永远空结果（比不做更伤信任）

## 4. 数据与 Store 对称设计（草案）

### 4.1 类型扩展

```typescript
interface HotelSearchSession {
  request_key: string;          // city-checkin-checkout-guests
  fetched_at: string;
  ranked: HotelQuote[];
  purchase_url: string;
  warnings: string[];
  confirmed_quote_id?: string | null;
  hide_ranked?: boolean;
}

interface TravelIntel {
  // ...existing
  last_hotel_search?: HotelSearchSession | null;
}

interface ConfirmedHotelStay {
  // 扩展至与 06 §3.3 一致
  quote?: HotelQuote;
  quote_id?: string;
  lat?: number;
  lng?: number;
  address?: string;
  purchase_url?: string;
  // is_primary：该城主酒店
}
```

### 4.2 Store（对称航班）

| Action | 作用 |
|--------|------|
| `setHotelSearchResult` | P5b：写入 ranked |
| `mergeHotelSearchResult` | P5b：stale 搜索 |
| `confirmHotelQuote` | 报价 → `hotels[]`，`hide_ranked` |
| `addManualHotelStay` | P5a：Trip 订好后手填 |
| `removeHotelStay` | 移除 + `syncHotelSearchAfterStayRemoval` |

### 4.3 `syncTravelIntelStatus` 需改

当前（仅航班）：

```typescript
if (intel.flights.length === 0) return { ...intel, status: 'draft' };
return { ...intel, status: 'partial' };
```

建议（机酒并重）：

| flights | hotels | status | 含义 |
|---------|--------|--------|------|
| 0 | 0 | `draft` | 均未确认 |
| ≥1 | 0 | `partial` | 仅航班（Q1 允许先生成） |
| 0 | ≥1 | `partial` | 仅酒店（玩法先行补酒店） |
| ≥1 | ≥1 | `confirmed` 或 `partial` | 视产品是否要求「机+酒齐备」才标 confirmed |

与 **Q1：不硬阻塞 generate** 一致：`partial` 即可进入阶段 C，generate Prompt 按有无酒店发 warning。

## 5. 业务差异：不能照搬的交互

| 航班 | 酒店 | 影响 |
|------|------|------|
| 单程 / 往返组合 | **多段入住**（同城换店、多城） | 确认单元是「一段 stay」，非 bundle |
| `origin/destination` + 日期 | `city` + `check_in/check_out` | 表单字段不同 |
| `role: outbound/return/intercity` | `is_primary` per city | 排序与覆盖校验 |
| 转机 `route_label` | 无 | 展示 name + 区域 + 星级 |
| Ignav 10～40s | 未知（爬虫/API 各异） | loading 文案需单独测 |
| 移除 bundle 两程 | 移除一段 stay；**间隙日**需警告 | P6 `check_in/check_out` 校验 |

**多酒店示例**（[06 §3.3](./06-机酒确认与行程生成流程方案.md)）：

| sequence | city | check_in | check_out |
|----------|------|----------|-----------|
| 1 | 新加坡 | 10-16 | 10-19 |
| 2 | 吉隆坡 | 10-19 | 10-22 |

每段独立确认；generate 时 LLM 知 10-19 换城需衔接 `flights[intercity]`。

## 6. 分期实施建议

### P5a — UX 壳 + 手动（**可立即对称航班 P3**）

| 步 | 内容 | 复用航班 |
|----|------|----------|
| 1 | `leftPanelMode: 'hotel'` + `InputPanel` 布局 | ✅ 复制 flight 分支 |
| 2 | `HotelIntelPanel` + `HotelManualAddPanel` | ✅ 复制 Manual 模式 |
| 3 | Trip.com 酒店 deep link（city + 日期） | ✅ 同 flight purchase_url |
| 4 | badge 三态 + 确认后切 form | ✅ |
| 5 | 航班 CTA「继续确认酒店」 | ✅ 改一行 store/Panel |
| 6 | 扩展 `syncTravelIntelStatus` 计酒店 | ⚠️ 小改 |

**不做**：搜索按钮 / ranked 卡片（无 API）。

### P5b — 结构化搜价（**待数据源**）

| 前置 | 内容 |
|------|------|
| `POST /hotels/search` 或 Apify 原型 | `HotelQuote[]` normalize |
| Partner / Places | lat、评分、税费说明 |
| 然后 | 原样复制：`setHotelSearchResult`、stale loading、`confirmHotelQuote`、`hide_ranked` |

### P6 — 多酒店校验

- 日期落在 `trip_request.date_start/end` 内

- 总览图 cross_day 与 `is_primary` 对齐

## 7. 与阶段 C 的衔接

| 时机 | 行为 |
|------|------|
| 仅确认航班 | generate + warning「未确认酒店」 |
| 确认首晚 `is_primary` | Prompt 硬约束 Day1 晚宿附近 geo |
| 机酒均确认 | `intel_ready` 软标记；减少 warning |
| 玩法先行 `skipped` | 占位 hotel 节点，supplement 后补 |

P4（generate 读 intel）应 **航班与酒店同时读**，但 **不阻塞 P5a**：无酒店时行为与今日一致。

## 10. 最终回答

**酒店是否可以使用同样方式？**

- **UX / 流程 / TravelIntel 分层**：**可以，且应该**——否则阶段 B 会再次掉进 Chat 嵌套、确认后无 CTA 的坑。
- **Ignav 式搜价卡片**：**现在不能**——缺 API 与已验证数据源；应 **P5a 手动 + deep link 用同样壳**，**P5b 再挂 ranked**。
- **实施顺序**：P5a 可与 P4（generate 读航班）并行；不必等 Partner API，但应在 P5b 前扩展 `ConfirmedHotelStay` 与 `syncTravelIntelStatus`。
