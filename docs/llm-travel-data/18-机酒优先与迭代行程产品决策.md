## 2. 为何不必「玩法两轮生成」——机酒优先更好

### 2.1 结论

**两轮生成不是刚需。** 你提出的「先机酒、再玩法」更贴合 L2（行程服从抵达/离开/住宿），也更省一次不可靠的草图 LLM。

| 方案 | 优点 | 缺点 |
|------|------|------|
| 草图玩法 → 机酒 → 精排 | 玩法重心可倒推酒店片区 | 草图坐标易错；用户感觉「做了两遍」；与「先定机票」心智冲突 |
| **机酒 → 玩法（采纳）** | 时刻/机场硬约束清晰；一次精排即可；与现有 Flight/Stay Panel 对齐 | 酒店片区缺少「玩法重心」时只能用 **城市中心 / 用户偏好 / 热门片区启发式** |

机酒优先时，「去哪」对机票只需 **城市**（你已确认）；酒店片区用：表单偏好 + stay-zone 推荐（可带航班抵达机场）+ 用户确认，**不必先生成整张行程图**。

### 2.2 目标主路径

```text
表单（出发/目的城市/日期/人数/预算档/偏好）
  → [可选] 对话补全缺失字段（FormPatch）
  → 机票：按城 OD 搜 → 5:2:2:1 排序 → 人确认写入 travel_intel
  → 酒店：城市/片区 + 每晚预算带 → 深链列表意向 / 日后库存 API → 人确认
  → 玩法精排 generate：硬吃 flights + stay/hotel + 表单
  → 人继续改：改机酒 / 改节点 / 「在此基础上优化|重构」
```

与现状差距：**B-P4**（generate 吃 intel）+ 产品门禁「无确认航班则阻/强阻精排」+ 迭代入口设计（§4）。

## 3. Agent：要不要、怎么切

### 3.1 原则

现阶段 **不要** 上完整多 Agent 编排（Planner 中枢）。优先：

1. **确定性管道**（搜价、打分、围栏 geocode、深链）  
2. **人确认**（机酒列表）  
3. **单次 LLM**（玩法精排 / 局部改写）  

「Agent」只在 **需要对话补全、意图路由、或带 tool 的多步推理** 时出现，且应是 **薄层**。

### 3.2 建议切分（逻辑角色，可先不做独立服务）

| 逻辑角色 | 是否独立 Agent | Phase 1 实现 | 输入 | 输出 |
|----------|----------------|--------------|------|------|
| **表单补全** | 否（已有 Chat FormPatch） | 加强必填校验与追问 | 用户话 + 残缺表单 | FormPatch |
| **机票助手** | **暂不需要独立 Agent** | `search` + `rank(5:2:2:1)` + Panel 确认；Chat Tool `search_flights` 可选 | OD/日期/人数 | 排序列表 → `travel_intel.flights` |
| **酒店助手** | **暂不需要独立 Agent** | StayZone + Trip 深链；有库存 API 后再「区间内距离排序」 | 城/片区/每晚预算 | 确认 hotel / zone |
| **玩法 Agent** | **要，但是「精排/改写」单 LLM** | `generate` / `regenerate` / `optimize` 三种模式 | trip_request + intel + 可选现有 itinerary | 行程图 |
| **编排 Planner** | ⏸ | L1+L2 稳后再议 | — | — |

**机票不必单独 Agent 的原因**：排序公式已定、人确认已定；Agent 容易变成「编理由不改分」。Chat 里按需搜价用 **Tool** 即可（`B-FLT-01`），不是第二个大脑。

**玩法侧要「像 Agent」的原因**：约束多（机酒时刻、住宿、偏好、已有节点）、且要支持 **优化 / 重构**（§4）——用 **同一套 Prompt 契约 + mode 参数** 比再套一层 Planner 更可控。

### 3.3 表单信息不足时怎么补

当前 `TripRequest` 字段：出发/目的、日期或天数、人数、预算档、偏好标签、备注。对机酒优先仍 **偏瘦**：

| 缺口 | 建议（产品） | 优先级 |
|------|--------------|--------|
| 每晚酒店预算数字（或区间） | 表单项或由 `budget_level` 映射默认带 | P1（HOT-03） |
| 多城列表（曼谷+清迈） | `cities[]` 或目的地解析；与城际航段对齐 | P1（B-P3） |
| 抵达/离开灵活窗（±1 天） | 搜票日期窗 | P2 |
| 「到达是否要上午」等时刻偏好 | 进 5:2:2:1 的「到达」维 | P1（rank 增强） |
| 必去/不去 | notes 或 tags 结构化 | P2 |

补全路径：**表单必填门禁 → 对话追问 FormPatch → 再进机酒 Panel**。不要用「先瞎生成玩法」来反推表单。

## 4. 迭代旅行：编辑机酒 + 优化 / 重构

旅行不是一次性写死。建议把状态机写清：

```text
                    ┌──────────────┐
                    │  trip_request │◄── 可随时改表单（可能使 intel 过期）
                    └──────┬───────┘
                           ▼
                    ┌──────────────┐
         ┌─────────►│ travel_intel │◄────────┐
         │          │ flights/hotels│         │
         │          └──────┬───────┘         │
         │ 改航班/酒店      │                 │ 改机酒后
         │                 ▼                 │
         │          ┌──────────────┐         │
         │          │  itinerary   │─────────┘
         │          └──────┬───────┘
         │                 │
         │    ┌────────────┼────────────┐
         │    ▼            ▼            ▼
         │  局部编辑    optimize     regenerate
         │  (拖点/改时)  (保骨架)     (整表重排)
```

### 4.1 三种玩法模式（同一 generate 管道）

| mode | 用户心智 | 约束 | 行为 |
|------|----------|------|------|
| **`generate`** | 首次精排 | 必须有已确认航班（产品门禁）；酒店/片区尽量有 | 从零生成日程，硬吃 intel |
| **`optimize`** | 「在此基础上优化」 | 保留大部分节点/日序；可调顺序、换 POI、补交通 | Prompt：diff 式修改建议或直接出新图 + `preserved_node_ids` |
| **`regenerate`** | 「重构 / 推倒重来」 | 仍硬吃 **当前** intel + 表单；可丢弃旧节点 | 等同 generate，但可带「上一版吐槽」notes |

机酒编辑后：

- **不自动重跑玩法**（避免抢用户）  
- UI 提示：「航班已变，日程可能冲突」→ 按钮 **优化适配**（`optimize`）或 **按新机酒重构**（`regenerate`）  
- 校验层：抵达日过早活动、末班离开冲突 → `meta.warnings`（可先规则、后 LLM）

### 4.2 机酒编辑设计要点

| 点 | 建议 |
|----|------|
| 真相源 | `travel_intel` 为机酒锚点；地图 hotel 节点与 intel 双向同步（已有） |
| 改航班 | Panel 重搜 / 手动改 → `confirm` 覆盖对应 `role`+`sequence` |
| 改酒店 | 换片区或换店 → 更新 intel + 节点 |
| 过期 | 改 `date_*` / `destination` 时标记 intel `stale`，搜价前需确认 |
| 深链 | 始终展示为可点击链接，**从不** `window.open` 自动跳 |

### 4.3 与「先机酒再精排」门禁

| 条件 | 行为 |
|------|------|
| `flights.length === 0` | **阻断**首次 `generate`（或极强确认二次弹窗；推荐阻断） |
| 仅有去程无回程 | 允许，但 warning |
| 无酒店/片区 | 允许精排，warning「住宿未锚」 |
| 已有 itinerary + 改机酒 | 不阻断编辑；提示 optimize/regenerate |

## 5. 单城 / 多城：性价比逻辑能否一致？

### 5.1 结论：**可以一致**

性价比分的是 **「某一 OD + 日期窗上的候选报价集合」**，与「整趟有几个城市」无关。

| 维度 | 单城（往返） | 多城（A→B→C / 开放爪） |
|------|--------------|------------------------|
| 搜价单位 | 去程、回程（或往返组合报价） | **每一段** OD 各搜一次（或供应商多城报价若有） |
| 打分公式 | **同一** 5:2:2:1 | **同一** 公式，在 **该段候选集内** min-max |
| 人确认 | 列表确认 1～2 段 | 列表确认 N 段（`sequence`） |
| 全局最优 | 可选：往返组合价 vs 两单程 | Phase 1 **不做**跨段联合最优（组合爆炸）；各段独立 Top 列表即可 |

**可行**：多城 = 单城逻辑的 **重复应用** + `role: intercity` + 日期衔接校验（抵达 B 不能晚于下一活动日）。

**Phase 1 不做**：全行程「总花费最低」的联合搜索（需多城 API 或自研 DFS）；那是 L3+。

### 5.2 到达时刻维（权重 1）

单城回程「离开是否太早」与多城「城际是否半夜抵达」用同一 `time_fit` 启发式即可，例如：

- 抵达本地 0–6 点：罚分高  
- 6–10 / 20–24：中等  
- 10–20：优  

具体阈值可后调；**权重 0.1 已锁定**。

### 5.3 与现有 `rank.py` 差距

现状权重是 `balanced ≈ 0.45/0.45/0.10`（价/时/中转），**无到达时刻维**。  
采纳后改为约 **0.5 / 0.2 / 0.2 / 0.1**，并扩展 `RankPreference` 或新增 `value`（性价比）档。

## 6. 信息源现状（回答「是不是只有 Trip」）

### 6.1 机票：**不是只有 Trip**

| 源 | 作用 | 现状 |
|----|------|------|
| **Ignav** | App 内 **参考报价列表**（可排序） | ✅ 主搜价源 |
| **Trip.com** | **深链去下单/核价**（联盟） | ✅ 每条结果可挂链接；不自动打开 |
| **LetsFG** | Ignav 空时的 fallback | ✅ 可选 |
| Duffel 等 | 文档 Spike | ⏸ 未接主路径 |

多方比价：Phase 1 = **Ignav 排序 + Trip 下单**；第二报价源对比（LetsFG 并列展示）可后做，不必等。

### 6.2 酒店：**目前实质只有 Trip 深链**

| 源 | 作用 | 现状 |
|----|------|------|
| Trip.com 酒店列表深链 | 用户自开页挑选 | ✅ P5z |
| 库存 API（Hotelbeds / Trip Partner） | App 内价+距排序 | ❌ 未接 → 即「无库存 API」 |
| Google Places lodging | 名+坐标+口碑，无 OTA 价 | 未接 |

因此酒店 Phase 1：**片区推荐 + 深链贴出 + 人确认店名/位置**；不能承诺 App 内「每晚含税可比价列表」。有第二源后再「多方对比」。

### 6.3 「无库存 API」含义（答 B7）

是的：**没有**能在服务端稳定返回「可订房价 + 库存」的结构化 API。  
不等于不能给链接——**链接展示在 UI 内，用户点击再打开；禁止自动打开浏览器/新标签。**
