## 0. 结论摘要

| # | 结论 |
|---|------|
| 1 | **缺能力**：现网没有「分析用户提示词 → 规范主题 tag → 挂到片区」的独立管道；32 的 `fit_tag` 是另一回事。 |
| 2 | 主题远不止「海边 / 人文」：至少覆盖 **玩法品类、同行结构、节奏预算、空间环境、约束禁忌、具名必去** 六大类。 |
| 3 | 抽取应 **词表规则（可测）+ LLM 补全（可漂移）**；展示用用户语言短标签，内部用稳定 `theme_id`。 |
| 4 | 片区卡展示的是 **「该区命中了用户的哪些主题」**，不是把全部用户主题无差别贴在每张卡上。 |
| 5 | 机酒状态（`fit_tag`/`bookable`）可保留为次要角标；**主视觉应是 `theme_tags`**。 |

```text
free_text + preference_tags + notes（+ 可选贴链摘要）
        ↓  ThemeExtract
  theme_tags[]（规范 id + 展示文案 + 证据片段）
        ↓  ZoneAlign（LLM/规则）
  每个 zone.matched_themes[] / unmatched 提示
        ↓  UI 卡顶
  [海边][美食] …   （另：小字「需换城」若仍保留）
```

## 1. Skill 分析方法

| Skill | 用于本分析 |
|-------|------------|
| **llm-api-engineering** | 主题抽取与 HARD/机酒隔离：主题是 `USER_DATA` 软信号，不能覆盖航班/目的地；输出须结构化可校验 |
| **ai-chat-ui** | Tag 是只读摘要信号；改偏好仍走对话/FormPatch 确认，不在卡片上直接改提示词 |
| **ui-ux-pro-max** | 卡顶 tag **有可读 label**；控制数量（建议 ≤3～4/卡）；勿用纯色块无文字 |

刻意不把 RollingGo 设施 tag（泳池/含早）与用户意图 tag 混为一谈——前者是酒店供给，后者是需求意图。

## 2. 与 32 的分工（避免再混）

| 字段 | 含义 | 例子 | 门禁？ |
|------|------|------|--------|
| **`theme_tags` / `matched_themes`** | 提示词主题 | 海边、人文、亲子 | 否（展示+排序加权） |
| **`fit_tag` / `bookable`** | 与当前机酒锚点关系 | 当前锚点、需换城 | 是（能否锁店） |

用户本次纠正后：**主展示 = 主题 tag**；状态 tag 可降为次要或图标。

## 3. 主题可能性全景（不止海边/人文）

> 来源对齐：项目 `preference_tags` 示例、demo 关键词、[03 品类](./03-游玩项目.md)、[12 因子 E～S](./12-阶段B住宿区域倒推方案.md)、住宿 prefs。

### 3.1 玩法 / 空间氛围（最常进片区卡）

| 主题 id（建议） | 用户说法举例 | 对片区含义 |
|-----------------|--------------|------------|
| `seaside` | 海边、海滩、海岛、亲海 | 近海/度假岸线；内陆城易「不匹配」 |
| `culture` | 人文、文化、博物馆、历史、古迹 | 老城、文博聚区 |
| `food` | 美食、小吃、夜市、米其林 | 餐饮聚集带、夜市周边 |
| `shopping` | 购物、奥特莱斯、免税店 | 商圈 / mall 枢纽 |
| `nature` | 自然、徒步、登山、公园、雨林 | 近绿地/城郊门户，非纯 CBD |
| `photo` | 摄影、网红打卡、日出 | 观景带、天际线、特色街区 |
| `nightlife` | 夜生活、酒吧、夜游 | 夜生活区；与亲子/安静冲突 |
| `religion` | 寺庙、清真寺、朝圣 | 宗教场所周边、着装/安静 |
| `art` | 艺术、画廊、设计 | 艺廊区、文创园 |
| `theme_park` | 乐园、迪士尼、环球 | 乐园专属住宿带 |

### 3.2 同行与节奏（常被漏掉，但提示词极常见）

| 主题 id | 用户说法 | 对片区含义 |
|---------|----------|------------|
| `family` | 亲子、带娃、儿童 | 家庭友好、少酒吧街 |
| `elder` | 老人、父母、行动不便 | 少爬坡、近地铁、平坦 |
| `couple` | 蜜月、情侣、纪念日 | 景观/安静/浪漫岸线 |
| `solo` | 独行、背包 | 安全可见、交通方便 |
| `slow` | 慢游、发呆、不赶行程 | 非中转枢纽核心 |
| `packed` | 特种兵、排满、高效 | 更贴 POI 重心 / 枢纽 |

### 3.3 预算与住宿气质

| 主题 id | 用户说法 | 对片区含义 |
|---------|----------|------------|
| `budget` | 穷游、青旅、便宜 | 外围枢纽、青年区 |
| `luxury` | 奢华、五星、度假村 | 核心/海景/品牌带 |
| `quiet` | 安静、睡得好、远离喧嚣 | 避开夜生活主轴 |
| `workation` | 办公、wifi、长住 | 公寓/商务廊桥区 |

### 3.4 交通与约束（提示词里的「硬软边界」）

| 主题 id | 用户说法 | 对片区含义 |
|---------|----------|------------|
| `transit` | 地铁旁、少换乘、方便 | 强化枢纽（与默认权重同向） |
| `walkable` | 步行友好、少坐车 | 缩小半径、贴 POI 簇 |
| `no_flight_change` | 不改机票、就定这城 | 抑制「需换城」备选噪音 |
| `must_see` | 必去 XX、一定要看 | **具名锚点**（见下）而非泛主题 |

### 3.5 具名实体（不是泛 tag，但必须进「分析」）

提示词常混有：

- **必去 POI**：「一定要去滨海湾花园」→ 不是 `nature`，而是 `must_see:滨海湾花园`  
- **避雷**：「不去赌场 / 不去红灯区」→ `avoid:*`  
- **品牌**：「要星巴克旁 / 只住无印风」→ 弱主题或过滤条件  
- **否定偏好**：「不要逛街、别排夜店」→ 抽取时要 **极性**（positive / negative）

若只做「海边/人文」布尔，会丢掉否定与具名，导致片区仍推购物/夜生活。

### 3.6 时间与季节（影响「哪类区」而非「哪座城」）

| 信号 | 例子 | 片区暗示 |
|------|------|----------|
| 雨季 / 怕热 | 「十月别暴晒」 | 室内连通、mall+地铁 |
| 夜间抵达 | 「红眼航班」 | 首晚少换乘（偏状态，可与 fit 协作） |
| 节日 | 「圣诞市集」 | 季节性聚区 |

### 3.7 冲突与组合（分析层必须建模）

| 组合 | 风险 | 分析器应做什么 |
|------|------|----------------|
| 海边 + 已定胡志明 | 城与主题冲突 | 主题 tag 仍标「海边」；另用 fit 标需换城 |
| 亲子 + 夜生活 | 同城不同区 | 两区分别打不同 theme；勿合成一个糊 tag |
| 美食 + 安静 | 可能同区难兼得 | 允许多区，或 tag_note「鱼与熊掌」 |
| 只要人文、不要购物 | 极性 | `culture+` / `shopping-` |
| 空提示词 | 无主题 | 不硬造 tag；可仅保留状态角标 |

## 4. 「还存在什么可能性」——检查清单

除海边/人文外，实施前至少要能回答：

1. **多主题并存**（美食+亲子+拍照）如何抽、如何限展？  
2. **否定句**（不要 X）是否进入 avoid 列表？  
3. **具名必去** 是否单独结构，而非塞进泛 tag？  
4. **同行结构**（带老人/带娃）是否从自然语言推断，而不只靠 travelers 人数？  
5. **预算档** 与 `budget_level` / `hotel_budget_per_night` 如何去重？  
6. **英文/拼音/俚语**（beach、chill、特种兵）？  
7. **与已写 `preference_tags` 合并**：以提示词为准时，tags 字段是输入还是输出缓存？  
8. **贴链 UGC** 是否允许贡献主题（权重低于用户原话）？  
9. **主题→片区对齐失败**（用户要滑雪但目的地胡志明）如何展示「未命中」而非假命中？  
10. **过度抽取**（把「到海边城市玩两天」抽成全程海边）的抑制？

## 5. 推荐能力架构（分析级）

### 5.1 ThemeExtract（缺的就是这层）

**输入**：`free_text` · `notes` · `preference_tags` ·（可选）user_evidence 标题  

**输出**（建议）：

```json
{
  "themes": [
    {
      "id": "seaside",
      "label": "海边",
      "polarity": "positive",
      "confidence": 0.9,
      "evidence": "想去海边"
    },
    {
      "id": "must_see",
      "label": "必去:博物馆",
      "polarity": "positive",
      "entity": "某某博物馆",
      "confidence": 0.7,
      "evidence": "一定要去博物馆"
    }
  ],
  "unresolved": []
}
```

**实现策略（llm-api）**：

| 层 | 职责 |
|----|------|
| **规则词表** | 高置信同义词 → id（可单测）；含否定前缀「不要/别/别去」 |
| **LLM JSON** | 补词表外说法、具名实体、冲突说明；temperature 低；校验 id ∈ 白名单或 `custom:*` |
| **合并** | `preference_tags` 已有项直接升格；与 free_text 去重 |

### 5.2 ZoneAlign

每个候选 zone 增加 `matched_themes: [{id,label}]`：

- 同城枢纽区可能 **匹配 0 个** 海边主题 → 卡顶可不显示海边，或灰显「未覆盖：海边」  
- 芽庄备选 **匹配海边**  
- 禁止：用户没提的主题出现在卡顶（幻觉）

### 5.3 UI（ai-chat-ui）

- 卡顶：**主题 tag 为主**（用户语言）  
- 次要：需换城等状态（若保留）  
- 全局一条：「已从描述识别：海边 · 亲子」——证明分析发生过  
- 每卡最多 3～4 个主题 tag，溢出 `+N`

## 6. 与现有代码的差距

| 已有 | 缺口 |
|------|------|
| `preference_tags` 存储 + FormPatch | 无统一 ThemeExtract；demo 仅 7 词硬匹配 |
| 32 `fit_tag` 机酒状态 | 不是提示词主题 |
| `zone_tags.detect_preference_themes` 仅 seaside/food/nature | 覆盖面窄、无极性/具名、未驱动卡顶主展示 |
| StayZone `scenery` 等 prefs | 表单滑杆，不来自自然语言分析 |
| 行程 generate 吃 preference_tags | 片区卡不消费「分析后的主题」 |

## 7. 建议实施顺序

```text
1. ThemeExtract 服务（中文规则词表 v1 + custom:原词 + 单测）→ 可先不接 LLM  ✅
2. Schema：运行时/meta themes + zone.matched_themes / uncovered_themes（不写回 preference_tags） ✅
3. UI：卡顶主题 tag 为主；未命中主题在锚点卡明示；fit_tag 降级 ✅
4. ZoneAlign：粗推按 themes 列区并回传 matched ✅
5. LLM 补抽取 + 否定/具名（第二波） 🔲
```

### 7.1 已拍板（2026-08-10）

| Q | 决定 |
|---|------|
| **Q1** | **允许** `custom:用户原词`（白名单 id + 自定义并存） |
| **Q2** | **是**：锚点卡上明示「未覆盖」的主题（如城内枢纽未覆盖「海边」） |
| **Q3** | **先不写回** `preference_tags`；仅运行时 / `meta`（或推荐响应字段） |
| **Q4** | **非 P0**：用户一般用中文；词表与抽取以中文为主，英文不做优先 |

## 8. 一句话

缺的不是「再多个海边枚举」，而是 **提示词主题分析器 + 片区命中对齐**；可能性覆盖玩法、同行、预算气质、约束禁忌、具名必去与否定句——海边/人文只是其中两格。
