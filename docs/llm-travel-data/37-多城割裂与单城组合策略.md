# 37 · 多城割裂感：单城组合 vs 一步到位多城

> **日期**：2026-08-12  
> **结论（拍板建议）**：**做多个单城段组合（leg / city segment）**，不要一步到位「全局多城联合规划」。  
> **关联**：[18 §5](./18-机酒优先与迭代行程产品决策.md) · [32](./32-住宿粗推多片区与偏好Tag实施.md) · [38 实施拆解](./38-多城城段实施影响与联动改动.md) · [39 先去哪决策](./39-多城先去哪决策因子.md) · [问题日志 P133](../问题日志/01-开放中.md#p133) · P128 / P131 / P122

---

## 1. 用户现象

规划体验「很割裂」：航班、酒店、玩法像三套工具；一旦行程跨城（胡志明→芽庄、奥克兰→罗托鲁瓦、曼谷→清迈），割裂更明显。

推测正确：**产品叙事与数据模型仍是单城**，多城只在航班 UI 上「能追加航段」，下游没有同一套城段契约。

---

## 2. 现状能力分层（代码事实）

| 层 | 单城假设 | 多城现状 |
|----|----------|----------|
| `trip_request` | 单一 `destination: string` | 无 `cities[]` / 无城段日期窗 |
| 航班 | 一程 OD 搜价 | **B-P3 UI**：多城/城际模板可 `sequence` 追加腿；**非**联合报价 |
| 住宿 | 一片区/一店锚 → 日闭环 | `fit_tag=needs_city_change` **禁止确认**；换城被当冲突而非下一段 |
| 生成 | HARD = 确认航班 + **同一批** confirmed_hotels；geocode fence ≈ 一个 destination | 多酒店 `covers_day` 有字段，但换店/围栏仍易全局化（见 P128、P122） |
| 地图 / 印证 | 一城 closed pool / fence | 跨城钉易漂；印证串城靠弱过滤 |

文档 [18 §5](./18-机酒优先与迭代行程产品决策.md) 已写死：

> 多城 = 单城逻辑的 **重复应用** + `role: intercity` + 日期衔接。Phase 1 **不做**跨段联合最优。

航班侧基本按此做了；**住宿 + 生成 + 表单目的地** 未闭合，故用户感到割裂。

---

## 3. 两条路对比

### A. 多个单城组合（推荐）

**定义**：一趟 Trip = 有序 **城段** `segments[]`；每段自带日期窗、进出港航班（或城际）、本城酒店、本城玩法；段与段之间只有「交通日 / 城际腿」。

| 优点 | 缺点 |
|------|------|
| 复用现有机酒门禁、片区、closed pool、日闭环 | 要显式「城段」UI 与 schema |
| 与 18 / travel-product-flow 一致：确认-before-expensive | 跨段「总花费最低」不做（可接受） |
| 换店/围栏可 **scoped 到段**（顺带治 P128） | 用户要理解「先定段再填段」 |
| 可渐进：先 UI 分段，再 generate 吃多酒店 covers_day | — |

### B. 一步到位多城计划（不推荐作下一里程碑）

**定义**：一次表单填多城，一次搜多城联运，一次 LLM 出跨城全图，全局优化机酒玩法。

| 优点 | 缺点 |
|------|------|
| 叙事「一趟旅行一个按钮」 | 组合爆炸；无多城库存/联运主 API |
| — | 与 FLOW-01c「先锁机酒再生成」冲突 |
| — | geocode / 印证 / 片区全部要重做国家级路由 |
| — | 失败时整趟不可用，难局部重试 |

**结论**：B 是 L3+；现在做会放大 P122/P128/P131 类问题，而不是消灭割裂。

## 4. 推荐产品形态（A 的落地形状）

```
TripRequest
  destination          ← 兼容：主目的地 / 国家名（展示用）
  cities[] 或 segments[]  ← 真相源
    { city, date_start, date_end, role?: hub|leg }
travel_intel
  flights[]            ← 已有 sequence / intercity
  hotels[]             ← 每段 ≥1 锁定店；covers 对齐段日期
generate
  HARD = 各段航班+酒店列表
  日归属 = 段日期窗；换城日 = transit / airport 节点
UI
  「城段时间线」：段1 机酒 → 段2 机酒 → … → 生成玩法
  需换城 tag →「加为下一段」而非永久禁用
```

与开放项衔接：

| ID | 关系 |
|----|------|
| P128 | 换店必须按 **段/酒店 id**，禁止全行程日闭环覆盖 |
| P131 | 片区目录是 **段内** 的；多城不是多给几个 LLM zone |
| P122 | 玩法围栏按 **当日所属城段**，不是整趟 destination 字符串 |
| P129 | 城际边必须真 Directions / 航班时长，禁止 20min |

## 5. 实施阶段（建议）

| 阶段 | 做什么 | 不做 |
|------|--------|------|
| **MC-0 叙事** | 摘要/下一步卡显示「当前城段」；多城航班已存在时提示「请为本段锁店」 | 改 generate |
| **MC-1 schema** ✅ | `segments[]`（或 `cities[]`+日期）与 `destination` 兼容；门禁：每段锁店才可生成 | 联合搜价 |
| **MC-2 住宿** ✅ | 需换城 → 一键「创建下一段」；锁店 scoped；片区检索带 `segment.city` | 全国酒店池 |
| **MC-3 航班** ✅ | 确认腿写 `segment_id`；城际→ensure 加段；下一段预填下一城 | 联合报价 |
| **MC-4 生成** ✅ | HARD 注入多段酒店+城际日；geocode bias 按日所属城 | 一次全局最优 LLM |

---

## 6. 一句话答复用户

**做多个单城组合更好。**  
航班已按「多段单城」在走；割裂来自目的地/酒店/生成仍按一个 `destination` 闭环。下一步应补 **城段模型 + 分段锁机酒**，而不是上「一步到位多城联合规划」。
