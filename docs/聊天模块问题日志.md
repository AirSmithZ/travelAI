## 一、前端样式问题

审查依据：`ai-chat-ui` 布局/确认卡/滚动约定；`design-taste-frontend` 间距、层级、动效克制。

### P67 · 确认面板挤占消息区（高）

**现象**  
`ChatPanel` 布局为：`ChatMessageList` → `PatchConfirmPanel` → `ChatComposer`。有待确认 patch 时，面板固定在消息列表与输入框之间，且含多字段表单 + 四按钮，左栏窄时消息区高度可低于 150px。

**对照 skill**  
`ai-chat-ui` 建议 Patch 确认卡**嵌入消息流**（assistant 消息下方），消息区 `flex:1; overflow-y:auto`，Composer 固定底。

**涉及文件**  
`ChatPanel.tsx`、`PatchConfirmPanel.css`

**建议**  
- 将确认卡作为 assistant 消息的子块渲染（`ChatMessageBubble` + `PatchConfirmCard`）  
- 或确认面板改为可折叠 / 抽屉，默认不占用消息区主高度

---

### P68 · 消息 patch 元数据未展示（高）

**现象**  
`addChatMessage` 会把 `patches` / `patch_status: 'pending'` 写入 assistant 消息，但 `ChatMessageBubble` 只渲染 `content` 文本。用户上翻历史时无法对应「哪条回复产生了哪些待确认项」。

**对照 skill**  
`ai-chat-ui`：「LLM 返回 patch → 卡片展示 → 用户确认」；同屏多个 patch 纵向排列。

**涉及文件**  
`ChatMessageBubble.tsx`、`ChatPanel.tsx`、`PatchConfirmCard.tsx`（`interactive` 变体已存在但未用于消息列表）

**建议**  
在产生 patch 的 assistant 消息下方内嵌 `PatchConfirmCard` 摘要；底部 `PatchConfirmPanel` 仅作当前步骤编辑，或二选一。

---

### P69 · patch_status 永不更新（中）

**现象**  
确认 / 忽略 patch 后，`pending_patches` 被清除，但历史 `chat_messages[].patch_status` 仍为 `pending`，`patches` 仍保留。

**影响**  
无法从对话历史判断某轮修改是否已应用；后续若做「按消息回溯」会数据不一致。

**涉及文件**  
`usePlanStore.ts`（`confirmPatches` / `dismissPatches`）

**建议**  
确认/忽略时按 `batch_id` 或 patch id 回写对应 assistant 消息的 `patch_status` 为 `applied` / `rejected`。

---

### P70 · 选节点打断对话模式（高）

**现象**  
`selectNode` / `selectEdge` 在 `leftPanelMode !== 'form'` 时强制 `leftPanelMode: 'form'`，对话面板被折叠。  
`ChatPanel` 的 `selectedNodeName` 占位符（「针对「XX」用对话修改」）仅在用户**手动展开对话且节点仍选中**时生效，主路径不可用。

**对照 skill**  
`ai-chat-ui` supplement 模式应围绕当前选区理解指代；设计文档 L13 selection 依赖节点上下文。

**涉及文件**  
`usePlanStore.ts`、`InputPanel.tsx`、`ChatPanel.tsx`

**建议**  
- 选节点时不强制切表单，或提供「对话中保持选区」开关  
- 在 form 模式顶部常驻选区 chips（当前天/节点），展开对话时带入 `selection`

---

### P71 · health 检查无 loading 态（低）

**现象**  
`apiStatus === 'checking'` 时 header 不展示任何 API 徽章，用户首次打开不知是在检测还是正常。

**涉及文件**  
`ChatPanel.tsx`

**建议**  
增加 `chat-panel__api--checking` 灰色「检测中…」徽章。

---

### P72 · 顶部 banner 叠加（中）

**现象**  
`supplement-banner`、`offline-hint`、`llm_unconfigured`、`generating-hint` 可同时出现，均 `flex-shrink:0`，进一步压缩 `ChatMessageList`。

**对照 skill**  
`design-taste-frontend`：信息优先，特效/装饰不得遮挡主内容区。

**建议**  
合并为单一状态条（优先级：离线 > LLM 未配置 > 生成中 > 模式提示），或可关闭。

---

### P73 · 确认按钮层级不清（中）

**现象**  
`PatchConfirmPanel` 同时展示「稍后处理 / 忽略本步 / 确认全部 / 确认本步」四个同级 secondary/primary 按钮，窄屏换行后难以识别主操作。

**涉及文件**  
`PatchConfirmPanel.tsx`、`PatchConfirmPanel.css`

**建议**  
主按钮仅保留「确认本步」；次要操作收入「更多」菜单或弱化样式。

---

### P74 · ChatComposer.disabled 未使用（低）

**现象**  
`ChatComposer` 支持 `disabled`，`ChatPanel` 只传 `isLoading`，未传 `disabled`。

**涉及文件**  
`ChatComposer.tsx`、`ChatPanel.tsx`

---

### P75 · 双 Toast 可能叠层（中）

**现象**  
`AppShell` 与 `ChatPanel` 各自挂载 `Toast`，生成行程与聊天解析可能同时弹 toast，无统一队列。

**涉及文件**  
`AppShell.tsx`、`ChatPanel.tsx`、`Toast.css`

**建议**  
全局单例 Toast / 通知 store。

---

### P76 · 确认表单区高度受限（低）

**现象**  
`.patch-step__fields { max-height: 200px }`，一步含多个 trip_request 字段或 add_node 块时需滚动，与外层消息区双重滚动体验差。

**涉及文件**  
`PatchConfirmPanel.css`

## 二、前后端交互问题

审查依据：`llm-api-engineering` 结构化输出、超时重试、可观测性、反模式清单。

### P77 · health 检查超时过长（中）

**现象**  
`fetchHealth()` 使用 `parseTimeoutSignal()`（120s），后端不可达时 health 检查长时间挂起，`apiStatus` 停留在 `checking`。

**对照 skill**  
health 探针应短超时（连接 10s 量级）。

**涉及文件**  
`api/chat.ts`

**建议**  
独立 `HEALTH_TIMEOUT_MS = 5000`；与 parse 超时分离。

---

### P78 · 前端无 502 重试（中）

**现象**  
后端对 LLM 429/502/503 有指数退避；前端 `parseChatMessage` 一次失败即 toast + 错误 assistant 消息，用户需手动重发。

**涉及文件**  
`api/chat.ts`、`ChatPanel.tsx`

**建议**  
对 502/503 做 1–2 次有限重试，或展示「重试」按钮而非仅错误文本。

---

### P79 · dropped_patch_count 未突出展示（低）

**现象**  
后端返回 `dropped_patch_count` 与 `warnings`，前端仅在「有 patches 时」把 `warnings[0]` 拼进 toast；**无 patch 且全部被丢弃**时依赖 warnings 文案，count 未单独展示。

**涉及文件**  
`ChatPanel.tsx`、`api/chat.ts`

---

### P80 · 完整 itinerary 重复上传（中）

**现象**  
supplement 模式每次 parse 将完整 `itinerary` 放入请求体；长行程（多 day × 多 node）payload 大、序列化耗时，Mobile/慢网下明显。

**对照 skill**  
`llm-api-engineering`：注入上下文应克制；后端已有 `_itinerary_summary` 压缩逻辑，但前端仍传全量。

**涉及文件**  
`ChatPanel.tsx`、`chat_parse.py`

**建议**  
- 前端 supplement 模式仅传 `itinerary_id` + `selection`，或  
- 后端改为只接受 summary 字段，全量 itinerary 从服务端缓存/会话读取

---

### P81 · chat_mode 纠正不同步（中）

**现象**  
后端 `align_chat_mode()` 按 `plan_phase` 纠正 `chat_mode` 并通过 `warnings` 告知；前端下次发送仍用 `resolveChatMode(plan.phase)` 本地推导，若 phase 与 UI 模式标签短暂不一致会重复警告。

**涉及文件**  
`chat_parse.py`、`ChatPanel.tsx`

**建议**  
响应中返回 `chat_mode_used`，前端写入 store 或下轮请求沿用服务端值。

---

### P82 · 自动 generate 失败无用户反馈（高）

**现象**  
`confirmPatches` 在 trip_request patch 确认后 `void maybeAutoGenerateItinerary()`，失败时（API 错误、mock 回退）不向 ChatPanel 反馈，用户以为「已自动生成路线图」。

**涉及文件**  
`usePlanStore.ts`、`ChatPanel.tsx`（emptyHint 写明「确认后将自动生成路线图」）

**建议**  
- `maybeAutoGenerateItinerary` 返回结果，ChatPanel / store 订阅并 toast

---

### P83 · Demo 与正式文案矛盾（中）

**现象**  
- 正式：`ChatPanel` emptyHint →「确认后将自动生成路线图」  
- Demo：`chatDemo.ts` →「不会自动生成行程」

离线演示与联调体验不一致，易误导测试。

**涉及文件**  
`chatDemo.ts`、`ChatPanel.tsx`

---

### P84 · 非流式 parse，loading 反馈弱（低）

**现象**  
`streamingHint` 为固定文案「正在解析你的需求…」，非 token 流；长时间 LLM 等待期间无进度细分。

**对照 skill**  
`ai-chat-ui` 流式模式 A 可接受，但应 disable 输入 + 光标动画；当前已有 `▍` 光标，**无阶段提示**（解析中 / 校验中）。

**涉及文件**  
`ChatPanel.tsx`、`chat.py`（无 SSE）

**说明**  
若保持非流式，至少按耗时升级 hint（30s 提示「仍在解析，请稍候」）。

---

### P85 · 无请求幂等键（低）

**现象**  
用户双击发送或网络重试可能导致重复 user 消息 + 重复 parse（`isLoading` 有 guard，但快速双击边界仍可能存在）。

**对照 skill**  
`llm-api-engineering`：解析类请求应支持 `request_id` 幂等。

**建议**  
前端生成 `client_request_id`，后端短期去重或前端发送后立即 disable 至响应完成（已基本做到）。

---

### P86 · supplement add_node 无地理编码（中）

**现象**  
global 模式首次 `generate` 时后端 `geocode_itinerary` 补坐标；supplement 通过对话 `add_node` 确认后仅 `applyItineraryPatch` 写前端 store，新节点 `lat/lng` 常为 0，**不触发后端 geocode**。

**涉及文件**  
`usePlanStore.ts`、`applyItineraryPatch.ts`、`itinerary_llm.py`

**建议**  
确认 add_node 后调用 `POST /itineraries/geocode-nodes`（或 generate 子路径）仅补缺失坐标；与产品约定「仅首次 generate 自动 geocode，其余手动」时需改 UI 提示。

---

### P87 · selection 与总览模式错位（低）

**现象**  
`buildSelection` 使用 `activeDayIndex + 1`；用户在总览图（`graphViewMode: 'overview'`）选节点时 `activeDayIndex` 可能不是节点所在天。

**涉及文件**  
`ChatPanel.tsx`、`usePlanStore.ts`

**建议**  
有 `selectedNodeId` 时从 `findNodeContext` 推导 `day_index`。

---

### P88 · JSON 围栏未剥离（低）

**现象**  
`LLMClient._parse_completion` 直接 `json.loads(content)`；模型若输出 ` ```json ... ``` `（未遵守 prompt），修复轮前即失败。

**对照 skill**  
「永远假设模型会输出脏 JSON」— 应有一层 strip fences 再 parse。

**涉及文件**  
`llm_client.py`

---

### P89 · FormPatch 工具层缺失（高）

**现象**  
LLM 返回的 patch 字段可能超出表单 schema（如非法 key、类型不符），前端确认后直接写入 store，导致静默丢弃或脏数据。

**对照 skill**  
`llm-api-engineering`：结构化输出需 Pydantic 校验 + 白名单；`ai-chat-ui`：「LLM 返回 → 用户确认 → 更新表单」需可靠闭环。

**涉及文件**  
`form_patch_tool.py`、`chat_parse.py`、`formPatchTool.ts`、`usePlanStore.ts`

**修复**  
- 后端 `process_llm_patches()` 按白名单过滤、类型规范化  
- 前端 `sanitizeFormPatch` / `applyFormPatches` 二次校验后写入
