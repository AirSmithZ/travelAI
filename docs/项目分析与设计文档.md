# AI 旅游行程规划系统 — 项目分析与设计文档

> 版本：v0.7 · 2026-06-29  
> 参考视觉：`map.png`（新加坡多日行程路线图）  
> 技术方向：Python 后端 + React 前端 + DeepSeek + Geocoding API + MapLibre 展示  
> 产品范围：**先做境外游** · 无登录 · 行程保存至 **localStorage** · **中文界面**

---

## 1. 项目概述

### 1.1 产品定位

用户用自然语言描述旅行意图（目的地、天数、偏好、预算等），系统通过 **AI 理解 → 联网检索 → 结构化行程生成**，输出两类互补视图：

| 视图 | 作用 | 类比 |
|------|------|------|
| **行程逻辑图** | 展示时间顺序、节点类型、路段耗时、交通工具、备选项 | `map.png` 的信息图 |
| **实景地图** | 展示真实地理坐标、当日路线连线、标点详情 | 地理落地层 |

两者通过 **日期 Tab + 视图 Tab（路线图 / 地图）+ 节点高亮联动**，让用户既能看懂「怎么玩」，也能看清「在哪里」。

### 1.2 核心价值

- **降低规划成本**：从模糊需求到可执行行程，分钟级生成
- **信息密度高但不乱**：参考 `map.png` 的色块编码 + 连线标注，一屏掌握多日安排
- **备选项可视化**：主路线实线、备选虚线，决策更直观
- **坐标由 AI 联网获取**：LLM 通过联网搜索补全 POI 名称与经纬度，地图侧只负责展示
- **本地可控**：无需注册登录，行程保存在浏览器 localStorage，随时继续编辑
- **格式强约束**：无论用户输入什么，LLM 必须输出统一 JSON Schema，前端零猜测渲染

### 1.3 已确认产品决策

| 决策项 | 结论 |
|--------|------|
| 目标市场 | **先做境外游**（新加坡等海外目的地） |
| 用户体系 | **无需登录**，匿名使用 |
| 数据持久化 | 行程保存至 **localStorage**，以 **TravelPlan** 为单位（§3.5） |
| 手动编辑 | **支持**：拖拽逻辑图节点、编辑节点内容与连线路径 |
| LLM | **DeepSeek**（OpenAI 兼容接口，配置见 `.env`） |
| 坐标来源 | **后端 Geocoding API**（主）+ Wikidata/web_search（辅）；见 §7.5 |
| 地图职责 | **展示 + 校准**：标点连线；低置信度时可点击/拖拽修正坐标 |
| 坐标确认 | **分级确认**：高置信度自动通过；中低置信度需用户确认（§3.6） |
| 主视图交互 | **Tab 切换**「路线图」与「地图」，非左右分屏 |
| 行程天数 | **无上限**，由用户输入决定；数据结构动态 `days[]` |
| 输出语言 | **中文**（节点名、tips、warnings 等） |
| 逻辑图布局 | 见 §2.6；**初版采用自由时间轴泳道 + 可拖拽** |
| 终端适配 | 需要适配手机，但排在 **最后阶段**（Phase 4） |
| 地图引擎 | **MapLibre + OSM**（免费瓦片，仅渲染） |

### 1.4 LLM 配置（`.env`）

后端通过环境变量读取，**密钥不入库、不写进文档**：

| 变量 | 当前值 / 说明 |
|------|---------------|
| `LLM_PROVIDER` | `openai`（OpenAI 兼容协议） |
| `LLM_MODEL` | `deepseek-v4-pro`（主生成模型） |
| `LLM_MODEL_REWRITE` | `deepseek-v4-flash`（查询改写 / 轻量任务） |
| `QUERY_REWRITE_ENABLED` | `true` |
| `LLM_THINKING_ENABLED` | `true`（深度思考模式） |
| `DEEPSEEK_API_KEY` | DeepSeek API 密钥 |
| `DEEPSEEK_API_BASE` | `https://api.deepseek.com/v1` |
| `CORS_ORIGINS` | `http://localhost:5173` 等前端地址 |

`.env` 中其余变量（Embedding、Rerank、Chroma 等）来自其他项目模板，**本旅游规划项目 Phase 2 仅需 LLM + 联网搜索相关项**，后续清理无关配置。

## 2. 参考设计拆解（map.png）

### 2.1 布局结构

```
┌─────────────────────────────────────────────────────────────┐
│  顶栏：日期 Tab（含星期、气温、天气图标）                      │
├──────────┬──────────────────────────────────────────────────┤
│ 左侧区域  │  主画布：按「日期列 × 区域行」组织的节点与连线       │
│ 分区标签  │  - 实线箭头：主路线                               │
│ (樟宜区   │  - 虚线：备选项 / 可选活动                         │
│  武吉士区 │  - 连线上标注：耗时、交通方式图标、时刻              │
│  万礼...) │  - 虚线框：同区域内节点分组（如机场 T1/T2）          │
└──────────┴──────────────────────────────────────────────────┘
```

### 2.2 节点类型与视觉编码（建议固化为 Design Token）

| 类型 | 示例 | 建议色 / 图标 | 数据字段 `category` |
|------|------|---------------|---------------------|
| 机场 / 航班 | 樟宜机场 T1 | 绿色 + 飞机 | `airport` |
| 酒店 | 酒店入住 | 灰色 + 床 | `hotel` |
| 餐厅 | 松发肉骨茶 | 深红 + 餐具 | `restaurant` |
| 小吃 | 叻沙、榴莲 | 橙色 + 碗 | `snack` |
| 游玩 | 动物园、博物馆 | 金黄 + 相机 | `attraction` |
| 地标 / 枢纽 | Jewel、地铁站 | 紫蓝 + 地标 | `landmark` |
| 交通节点 | 换乘、码头 | 青色 + 箭头 | `transit` |

### 2.3 连线语义

| 样式 | 含义 | 数据字段 |
|------|------|----------|
| 实线 + 箭头 | 主行程顺序 | `edge.type = "primary"` |
| 虚线 | 备选项 / 可替换节点 | `edge.type = "alternative"` |
| 虚线矩形框 | 同场景分组（航站楼、商场楼层） | `group.is_optional` |

连线上需展示：`duration_minutes`、`transport_mode`（步行/地铁/公交/打车/航班）、`depart_time` / `arrive_time`。

### 2.4 节点附属信息

- **楼层 / 子位置**：`L1`、`3L`（机场、商场内导航）
- **提示气泡**：换票点、安检提醒、着装建议（`tips[]`）
- **可选标记**：节点边框虚线 + `is_optional: true`

### 2.5 与实景地图的分工

| 行程逻辑图 | 实景地图 |
|------------|----------|
| 按时间轴泳道排版（语义布局） | 按经纬度排版（地理布局） |
| 强调类型、时间、备选关系 | **只读展示**标点与连线 |
| 适合「读计划」 | 适合「看位置」 |

**联动规则**：

- 顶栏 **日期 Tab** 在路线图与地图间共享，切换日期两边同步过滤
- 顶栏 **视图 Tab** 在「路线图」与「地图」间切换，同一区域全屏展示其一
- 点击路线图节点 → 自动切到地图 Tab（可选）并居中高亮对应 Marker
- 点击地图 Marker → 自动切到路线图 Tab（可选）并滚动到对应节点

**地图不做的事**：不提供地点搜索、不调用地理编码/路径规划 API、不反向查询 POI。所有坐标与路段信息均由 LLM 生成写入 JSON。

### 2.6 布局方案对比：网格 vs 自由时间轴

`map.png` 采用的是 **「日期列 × 区域行」网格布局**。文档初版也提到了 **「更自由的时间轴 / 泳道图」**，二者对比如下：

#### 方案 A：网格布局（map.png 风格）

```
         Day1          Day2          Day3
区域A  [酒店]──→[景点]   [午餐]──→[商场]
区域B              [博物馆]        [晚餐]
区域C  [机场]                              [酒店]
```

- **横轴**：日期（每一天一列）
- **纵轴**：地理区域（樟宜区、武吉士区…）
- **优点**：多日、多区域一览无遗；同一区域的活动垂直对齐，空间感强
- **缺点**：布局刚性，AI 自动排版复杂；用户拖拽后容易破坏列/行对齐；节点多时列内拥挤

#### 方案 B：自由时间轴 / 泳道图（推荐初版）

```
─── Day 1 ─────────────────────────────────────────
  06:00   08:30      12:00        15:00      18:00
   ●───────●─────────●────────────●──────────●
  机场    酒店      午餐        景点        晚餐
           ╎虚线
           ○ 备选餐厅A
           ○ 备选餐厅B

─── Day 2 ─────────────────────────────────────────
  ...
```

- **结构**：每个日期一条水平泳道（或竖向时间轴），节点按 **时间顺序** 从左到右排列
- **区域**：以泳道内的 **背景色带 / 分组框** 表达，而非强制占一行
- **备选项**：挂在主节点下方或右侧，虚线连接（与 `map.png` 一致）
- **优点**：
  - 更符合「时间流」直觉，用户一眼看懂先做什么后做什么
  - 与 **React Flow 自由拖拽** 天然契合——用户拖节点不会破坏整体结构
  - 手动编辑、插入/删除节点后，局部重排即可，成本低
- **缺点**：跨日、跨区域的「空间纵览」不如网格直观

#### 方案 C：混合（后续可选）

- 默认用 **时间轴泳道** 展示
- 提供「区域视图」切换：按区域折叠/展开，接近 `map.png` 的纵览感
- 用户拖拽后的坐标写入 `node.position`，下次打开从 localStorage 还原

**初版决策**：采用 **方案 B（自由时间轴泳道）**，保留 `map.png` 的 **节点配色、实虚线语义、连线标注** 不变；布局从刚性网格改为时间驱动的可编辑画布。

## 3. 功能模块

### 3.1 用户输入层

用户通过 **左侧输入面板**（§3.7）提供行程意图，含 **表单输入区** 与 **文字解析区（LLM 对话）**。

#### 3.1.1 结构化表单字段（TripRequest）

与 §6 `Itinerary`（生成结果）分离，输入层使用独立的 **`TripRequest`** 模型：

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `free_text` | `string` | 推荐 | 多行自然语言描述（中文为主，目的地可含英文） |
| `departure` | `string?` | 否 | 出发地 |
| `destination` | `string` | 是 | 目的地 |
| `date_start` | `string?` | 否 | 出发日期 `YYYY-MM-DD` |
| `date_end` | `string?` | 否 | 返程日期；与 `day_count` 可联动 |
| `day_count` | `number?` | 否 | 天数，**无上限** |
| `travelers` | `number?` | 否 | 人数 |
| `budget_level` | `'economy' \| 'comfort' \| 'luxury'?` | 否 | 预算：经济 / 舒适 / 奢华 |
| `preference_tags` | `string[]` | 否 | 偏好：美食、亲子、徒步… |
| `notes` | `string?` | 否 | 其他补充 |

#### 3.1.2 输入层行为

- 多行文本与结构化字段可 **双向同步**
- 天数 **不设上限**；`day_count` 与日期范围可联动计算
- **示例 prompt 模板** 一键填入
- 所有输入/对话归属 **当前选中的 TravelPlan**（§3.5）
- **「生成行程」** 将当前计划的 `TripRequest` 送后端 → 写入该计划 `itinerary`

#### 3.1.3 TripRequest 类型（草案）

```typescript
type BudgetLevel = 'economy' | 'comfort' | 'luxury';

interface TripRequest {
  free_text: string;
  departure?: string;
  destination: string;
  date_start?: string;
  date_end?: string;
  day_count?: number;
  travelers?: number;
  budget_level?: BudgetLevel;
  preference_tags: string[];
  notes?: string;
}
```

### 3.2 AI 分析与检索层

```
用户输入（TripRequest + 可选对话补丁）
  → 查询改写（deepseek-v4-flash，可选）
  → 意图解析（目的地、天数、偏好关键词）
  → LLM 联网搜索（景点/餐厅/酒店信息、排程、tips）
  → resolve_place：Geocoding API + Wikidata 解析坐标（§7.5）
  → 强制输出 Itinerary JSON（固定 Schema，中文内容）
  → Pydantic 校验 → 返回前端
  → 低置信度节点 → 坐标确认流（§3.6）
```

**关键原则**：

- LLM 负责**行程内容与 POI 名称**，坐标由 **`resolve_place` + 地图 Geocoding API** 解析
- 路段 `duration_minutes`、`transport_mode` 由 LLM 根据搜索结果推断
- **前端地图 Tab 不做 POI 搜索栏**；搜索/编码走后端 API 或编辑侧栏
- 无论用户输入什么，输出必须是 §6 定义的完整 `Itinerary` 结构

### 3.3 行程逻辑图渲染层

- **输入**：仅消费 §6 `Itinerary` JSON
- 顶栏：**路线图视图**（单日 | 总览）+ **预览 Tab**（路线图 | 地图）+ **日期 Tab**（单日模式下生效）
- 单日布局：时间轴泳道（§2.6 方案 B）；总览布局：区域行 × 日期列（§3.3.1，对齐 `map.png`）
- **手动编辑**：拖拽节点、侧栏编辑、增删节点/连线（与表单联动）

#### 3.3.1 路线图视图模式：单日 vs 总览

| 模式 | 展示范围 | 布局 |
|------|----------|------|
| **`day` 单日**（默认） | 当前日期 Tab 的 `days[i]` | 横向时间轴泳道 |
| **`overview` 总览** | **全部天数** 同时展示 | **最左区域轨 + 日期列** 网格 |

```
总览模式 layout（对齐 map.png）
┌──────────┬─────────────┬─────────────┬─────────────┐
│ 列头      │  Day1 10/16 │  Day2 10/18 │  Day3 10/19 │
├──────────┼─────────────┼─────────────┼─────────────┤
│ 樟宜区    │  ●──●──●   │             │             │  ← 左侧区域轨固定
│ 武吉士区  │             │  ●──●──●   │  ●──●       │
│ 万礼区    │             │             │  ●──●──●   │
└──────────┴─────────────┴─────────────┴─────────────┘
```

**区域数据来源**（优先级）：`ItineraryNode.region` → `DayPlan.region` → 兜底「其他」。

**实现要点（React Flow）**：

1. **RegionRail**（最左 ~80px，`sticky`）：去重后的区域名竖向排列
2. **日期列**：每列固定宽 ~300px；列头展示日期/星期/天气
3. **落位**：`layoutOverview()` 按 `(day_index, region)` 分组，列内 `dagre LR` 排节点
4. **连线**：列内主路线实线；跨日连接用跨列虚线弧（如有 edge）
5. **切换**：工具栏 `[单日] [总览]`；总览时日期 Tab 改为「聚焦滚动」或隐藏
6. **地图联动**：总览模式下地图展示 **全部天** Marker；单日模式仍过滤当日

```typescript
type GraphViewMode = 'day' | 'overview';
// ItineraryNode 增补
region?: string;  // 总览行定位，如「樟宜区」
```

组件：`OverviewGraphView.tsx`、`RegionRail.tsx`、`DayColumnHeader.tsx`、`layoutOverview.ts`。

**方案对比**：采用「区域×日期网格」因与 `map.png` 一致；纵向堆叠泳道区域感弱；单张大图多日易混乱。

### 3.4 实景地图层（展示 + 校准）

- **展示**：读取 `nodes[].lat/lng` 渲染 Marker + Polyline
- **校准模式**（编辑节点时进入）：
  - 点击地图空白处 → 更新节点坐标
  - 拖拽 Marker → 微调位置
  - 确认后 `coord_confidence` 置为 `manual`
- 日期 Tab：与路线图共享，`fitBounds` 自适应
- 地图瓦片：**MapLibre + OSM**（免费）；Geocoding 走后端 API，与瓦片解耦

### 3.6 坐标确认与校准（UX）

> **不需要每个节点都二次确认**——按置信度分级，避免打断流畅体验。

#### 何时需要用户确认？

| coord_confidence | 生成后行为 | 地图表现 |
|------------------|------------|----------|
| `high` | **自动通过**，直接落点 | 正常 Marker |
| `medium` | 落点但标黄；用户可忽略或点开确认 | 黄色描边 |
| `low` / `none` / `conflict` | **必须确认**后才能纳入最终路线 | 不落点或灰色「待确认」 |

生成完成后，若有待确认节点，弹出 **「坐标确认」面板**（非阻塞 Toast + 侧栏清单）：

```
┌─ 坐标待确认（2/5）────────────────────────┐
│  ○ 松发肉骨茶（克拉码头店）  [选择地点 ▼]  │
│  ○ 某小众咖啡馆              [在地图上选点] │
│                    [全部确认] [稍后处理]    │
└──────────────────────────────────────────┘
```

#### 三种校准方式（编辑侧栏内，按优先级推荐）

| 方式 | 交互 | 适用场景 | 推荐度 |
|------|------|----------|--------|
| **A. 下拉选择** | 输入店名 → 调后端 `geocode/autocomplete` → 选一条 POI 结果 | 有明确店名；**最常用** | ⭐⭐⭐ |
| **B. 地图点击/拖拽** | 切到地图 Tab → 点击落点或拖 Marker | 下拉搜不到；用户知道大概位置 | ⭐⭐⭐ |
| **C. 手动输入坐标** | 高级选项展开 lat/lng 数字输入 | 专业用户；有精确坐标 | ⭐ 折叠隐藏 |

**不推荐**每次生成都强制逐步确认——只对 `medium` 以下或用户主动编辑时触发完整确认流。

#### 下拉选择（方式 A）流程

```
用户输入「松发肉骨茶」
  → GET /api/v1/geocode/autocomplete?q=松发肉骨茶&city=新加坡
  → 后端调 Geocoding API（境外 Nominatim/Photon，境内高德）
  → 返回候选列表 [{ name, address, lat, lng, place_id }]
  → 用户点选一条 → 写入节点，coord_confidence = manual
```

#### 地图点击校准（方式 B）流程

```
编辑节点 → 点「在地图上选点」
  → 切到地图 Tab，进入选点模式（十字光标）
  → 用户点击 → 逆地理编码（可选，填充 address）→ 确认
  → coord_confidence = manual
```

#### 与「不做地图搜索」的关系

| 层面 | 做不做 | 说明 |
|------|--------|------|
| 行程自动生成时 | 后端静默调 Geocoding | 用户无感知，准确率更高 |
| 地图 Tab 顶部搜索栏 | **不做** | 避免与行程输入混淆 |
| 编辑节点侧栏 | **做** autocomplete | 属于校准，不是重新规划 |
| 地图点击选点 | **做** | 属于校准 |

### 3.5 旅行计划模块与本地存储

一切输入、对话、预览数据均归属 **当前选中的旅行计划（TravelPlan）**。用户须先 **选择计划** 或 **新建计划**，再操作表单 / 对话 / 路线图 / 地图。

#### 3.5.1 TravelPlan 数据模型

```typescript
type PlanPhase = 'empty' | 'planning' | 'detailed';

interface TravelPlan {
  id: string;
  title: string;
  created_at: string;
  updated_at: string;
  phase: PlanPhase;
  trip_request: TripRequest;
  itinerary: Itinerary | null;
  chat_messages: ChatMessage[];
  pending_patches: FormPatch[];
  form_layout?: FormLayoutState;
}
```

#### 3.5.2 计划选择器

入口置于 Header：**下拉选择当前计划** + **「＋ 新建旅行计划」**。

| 操作 | 行为 |
|------|------|
| 选择已有计划 | 加载该计划全部数据；有未保存修改时提示确认 |
| 新建计划 | `createEmptyPlan()`，**全量清空**（§3.5.3） |
| 重命名 / 删除 | 列表项菜单；**仅删除会移除计划数据**（§3.5.5） |

#### 3.5.5 数据清空与换目的地规则（已确认）

| 操作 | 是否清空/删除当前计划数据 | 行为 |
|------|---------------------------|------|
| **删除计划** | ✅ **唯一**主动清空入口 | 从列表移除该 `TravelPlan`；不可恢复（需二次确认） |
| **新建计划** | 不改动旧计划 | 创建新的空计划并切换；**旧计划完整保留** |
| **切换计划** | 否 | 仅切换 `active_plan_id` |
| **对话：换目的地/改去其他城市** | **否，不清空当前计划** | 见下方 **fork 新计划** 流程 |
| **重新生成行程** | 否（覆盖 itinerary） | 仅覆盖当前计划的 `itinerary`，不删计划本身 |

##### 换目的地：fork 新计划（非清空）

用户在 **supplement** 或 **global** 对话中说「不去新加坡了，改去曼谷」「换成东京」等 **目的地变更** 时：

```
LLM 识别为 destination_change（非普通 set patch）
  → 返回 patch: { action: 'fork_plan', new_destination, ... }
  → 确认卡：
     「将为「曼谷」创建新的旅行计划，当前「新加坡 4 日游」保留。
       [创建并切换]  [取消]」
  → 用户确认：
     1. newPlan = createEmptyPlan()
     2. 将 new_destination 及对话中提取的 day_count、偏好等写入 newPlan.trip_request
     3. newPlan.title = 「曼谷行程（草案）」或 LLM 建议名
     4. active_plan_id = newPlan.id
     5. **当前新加坡计划数据不动**
  → 新计划 phase=planning，右侧空态，对话走 global
```

```typescript
interface FormPatch {
  // ...existing
  action: 'set' | 'append' | 'remove' | 'add_node' | 'add_day' | 'fork_plan';
  fork_plan?: {
    destination: string;
    inherit_fields?: ('preference_tags' | 'travelers' | 'budget_level')[];
  };
}
```

| 规则 | 说明 |
|------|------|
| **禁止** | 在 supplement 模式下对当前计划执行 `set destination` 并清空 itinerary |
| **禁止** | 除删除按钮外，任何操作不得删除整个 `TravelPlan` |
| `inherit_fields` | 可选继承旧计划偏好/人数，**不继承** itinerary 与对话历史 |
| 后端校验 | `chat_mode=supplement` 时，若 patch 含 `destination` 变更，必须改为 `fork_plan` |

#### 3.5.3 新建计划：空状态规范（已确认）

| 区域 | 空状态 |
|------|--------|
| 表单 | `TripRequest` 全字段默认空 |
| 对话 | `chat_messages=[]`，不继承上一计划 |
| 路线图 | `itinerary=null` → 空态插画 |
| 地图 | 无 Marker / 连线 |
| 待确认 Patch | `pending_patches=[]` |

`phase` 推导：`全空→empty`；`有 request 无 itinerary→planning`；`有 itinerary→detailed`。

#### 3.5.4 持久化

- `localStorage.travel_plans_v1` 存 `TravelPlan[]` + `active_plan_id`
- debounce 自动保存当前计划
- 首次无计划 → 自动 `createEmptyPlan()`

#### 3.7.2 表单输入区

##### 两种绑定模式

#### 3.7.3 文字解析区（LLM 对话）

> 对话逻辑 **强依赖当前 TravelPlan 的 `phase`**，须与 §3.5、§3.7.8 一并阅读。

##### 对话分析模式（ChatAnalysisMode）

| 模式 | 触发条件（`phase`） | LLM 侧重点 | 典型产出 |
|------|---------------------|------------|----------|
| **`global` 全局分析** | `empty` 或 `planning`（无 Itinerary） | 目的地、天数、日期、人数、预算、偏好、整体方向 | 补全 `TripRequest` 的 FormPatch |
| **`supplement` 细节补充** | `detailed`（已有 Itinerary） | 在具体天数/节点上增补、替换、微调；**不默认推翻整份行程** | 针对 `Itinerary` 节点/边的 FormPatch |

```
                    ┌─────────────┐
  新建计划 ────────►│   empty     │  对话：global（从零收集需求）
                    └──────┬──────┘
                           │ 用户填表 / 对话确认 patch
                    ┌──────▼──────┐
                    │  planning   │  对话：global（完善 TripRequest）
                    └──────┬──────┘
                           │ 用户点「生成行程」
                    ┌──────▼──────┐
                    │  detailed   │  对话：supplement（补细节、加节点）
                    └─────────────┘
```

**模式判断（前端 → 后端）**：

```typescript
function resolveChatMode(plan: TravelPlan): 'global' | 'supplement' {
  return plan.phase === 'detailed' ? 'supplement' : 'global';
}
```

##### 两种模式的 Prompt 策略差异

| 维度 | `global` | `supplement` |
|------|----------|--------------|
| 上下文输入 | `trip_request` + 对话历史 | `trip_request` + **完整 `itinerary` 摘要** + 对话历史 |
| 允许 patch 目标 | 仅 `trip_request` 字段 |  primarily `itinerary` / `node` / `day`；`trip_request` 仅次要 |
| 禁止行为 | 输出 Itinerary 节点（未生成前） | 不得 patch 修改当前计划 `destination`；须走 `fork_plan`（§3.5.5） |
| 回复风格 | 「帮你梳理出行需求…」 | 「在第 2 天下午可以加…」「已有的松发肉骨茶可换成…」 |
| 示例用户话 | 「想去新加坡 4 天，带小孩吃美食」 | 「第二天下午加个动物园」「午餐换个素食餐厅」 |

##### 交互流程

```
用户在当前 TravelPlan 下输入
  → 解析 chat_mode = resolveChatMode(plan)
  → POST /api/v1/chat/parse {
       message,
       chat_mode,
       plan_phase,
       plan_id,
       trip_request,
       itinerary?,          // supplement 模式必传
       chat_history,        // 当前计划内最近 N 条
     }
  → LLM 按模式输出 { reply, patches[], mode_hint? }
  → UI 展示待确认卡片（§ 二次确认）
  → 用户确认 → 写入当前 TravelPlan（非其他计划）
  → global：更新 trip_request；supplement：更新 itinerary
  → 右侧按 phase 刷新
```

##### FormPatch 数据结构

```typescript
type PatchTarget = 'trip_request' | 'itinerary' | 'node' | 'day';

interface FormPatch {
  id: string;
  target: PatchTarget;
  action: 'set' | 'append' | 'remove' | 'add_node' | 'add_day';
  field_path: string;          // 如 "destination" / "preference_tags" / "days[1].nodes"
  label: string;               // 中文展示：「目的地」「偏好标签」
  old_value?: unknown;
  new_value: unknown;
  summary: string;             // 中文说明：「将目的地改为「东京」」
  confidence?: 'high' | 'medium' | 'low';
}

interface ChatMessage {
  id: string;
  role: 'user' | 'assistant' | 'system';
  content: string;
  chat_mode: 'global' | 'supplement';  // 记录产生时的模式
  patches?: FormPatch[];
  patch_status?: 'pending' | 'applied' | 'rejected';
}
```

补充：`supplement` 模式下 patch 类型扩展

| Patch 类型 | 示例 | `target` |
|------------|------|----------|
| 追加节点 | 「Day2 下午加滨海湾花园」 | `node` + `add_node` |
| 替换节点 | 「把午餐换成 XXX」 | `node` + `set` |
| 调整时段 | 「动物园改到早上 9 点」 | `node` + `set` |
| 追加备选项 | 「晚餐再加一家备选」 | `node` + `add_node` + `is_optional` |
| 调整交通 | 「改成地铁不要打车」 | `edge` + `set` |
| 全局变更（换目的地） | 「不去新加坡改曼谷」 | `fork_plan` → 新建计划并切换（§3.5.5） |

**`global` 模式禁止** 输出 `add_node` / `itinerary` 级 patch（尚未生成行程）。

##### 二次确认 UI（必做）

对话 **不得** 静默修改表单。每条 patch 渲染为确认卡：

```
┌─ 待确认修改 ─────────────────────────────┐
│  📍 目的地：新加坡 → 东京                  │
│  🏷 偏好标签：+「购物」+「动漫」             │
│  📅 天数：4 → 5                           │
│         [确认本条] [忽略]    [全部确认]     │
└──────────────────────────────────────────┘
```

| 规则 | 说明 |
|------|------|
| 默认态 | 所有 patch 为 `pending`，表单 **不变** |
| 确认单条 | 仅应用该 patch，`patch_status → applied` |
| 全部确认 | 批量应用当前消息内所有 pending patch |
| 低置信度 | `confidence: low` 时卡片高亮，建议用户核对 |
| 冲突 | 同一字段多条 patch 时只保留最新一条或让用户选 |
| 跨计划隔离 | patch 只写入当前计划；`fork_plan` 创建新计划 |

##### 对话可填充的范围（按模式）

**global**（`empty` / `planning`）：

| 用户话术 | 写入目标 |
|----------|----------|
| 「新加坡 4 天带小孩」 | `destination`, `day_count`, `preference_tags` |
| 「10 月中旬出发」 | `date_start`, `free_text` |
| 「预算舒适一点」 | `budget_level` |

**supplement**（`detailed`）：

| 用户话术 | 写入目标 |
|----------|----------|
| 「第二天下午加动物园」 | `days[1].nodes` + `edges` |
| 「午餐换素食餐厅」 | 对应 `ItineraryNode` |
| 「第三天加一家备选餐厅」 | `is_optional=true` 的节点 |

```
┌─────────────────────────────────────────────────────────┐
│                    Zustand Store                         │
│  plans: TravelPlan[]                                     │

│  activePlan: TravelPlan  // 派生：当前计划                │
```

#### 3.7.8 对话与计划：逻辑缺陷分析与规则

以下为当前设计需显式处理的 **逻辑缺口** 及 **已定规则**。

##### 已确认规则（来自产品决策）

| # | 规则 |
|---|------|
| R1 | 须先 **选择 / 新建** 旅行计划，所有 UI 数据挂在当前计划上 |
| R2 | **新建计划** → 表单、对话、路线图、地图 **全部为空** |
| R3 | **无 Itinerary** 时对话走 `global`，侧重需求收集 |
| R4 | **有 Itinerary** 时对话走 `supplement`，侧重细节补充 |
| R5 | 对话修改须经 **FormPatch 二次确认**，不静默写入 |
| R7 | **仅删除按钮** 可移除计划；换目的地 → **`fork_plan` 新建并切换**，不清空旧计划 |
| R8 | 路线图支持 **总览模式**：全天数 + 左侧区域轨（§3.3.1） |

##### 逻辑缺陷清单与对策

| # | 缺陷 | 风险 | 对策 |
|---|------|------|------|
| L1 | **切换计划时未保存修改** | 数据丢失 | 切换前 diff 检测；有变更则弹窗「保存 / 放弃 / 取消」 |
| L2 | **切换计划时 pending patch 残留** | patch 应用到错误计划 | patch 存入 `TravelPlan.pending_patches`；切换后只展示当前计划的 pending |
| L3 | **对话历史跨计划串台** | LLM 上下文混乱 | `chat_messages` **按 plan_id 隔离**；API 只传当前计划历史 |
| L4 | **新建计划后仍显示 Mock 数据** | 违背空状态 | 右预览 `itinerary===null` 时强制空态，不加载 demo |
| L5 | **global 模式输出 itinerary patch** | 右栏无法渲染 | 后端校验：global 模式 patch 仅允许 `target=trip_request` |
| L6 | **supplement 下换目的地** | 误清空行程 | 改为 `fork_plan`：新建空计划并跳转，**旧计划保留**（§3.5.5） |
| L7 | **phase 与 UI 模式不一致** | 对话侧重点错误 | `phase` 由 store 统一推导；`chat_mode` 派生于 `phase`，不由 LLM 决定 |
| L8 | **生成前后对话语义变化未告知用户** | 用户困惑 | 首次生成后对话区顶部展示轻提示：「已进入细节补充模式，可告诉我需要调整的节点」 |
| L9 | **空计划直接点生成** | 后端报错 | `destination` 必填校验；按钮 disabled + 表单高亮缺失项 |
| L10 | **删除当前活跃计划** | 页面无主 | 删除后自动选中列表第一项，或新建空计划 |
| L11 | **重新生成 vs 已有手动编辑** | 覆盖用户改动 | 点「重新生成」前确认：「将覆盖当前行程图与地图，是否继续？」 |
| L12 | **supplement 追加节点无坐标** | 地图无法落点 | 新节点 patch 确认后走 `resolve_place`；低置信度进 §3.6 |
| L13 | **多轮对话指代消解** | 「那天」「上面那家」解析错 | supplement 模式传入 `selection`（当前选中 day/node）作为 API 附加上下文 |
| L14 | **localStorage 无计划首次进入** | 空白不知干啥 | 首次访问自动 `createEmptyPlan()` 并选中 |
| L15 | **表单与对话同时改同一字段** | 冲突 | 以 **用户最后确认的操作** 为准；对话 patch 确认时展示与表单当前值 diff |

##### 计划切换状态机

```
[计划 A 编辑中]
    │
    ├─ 选择计划 B ──► 有未保存？─是─► 弹窗 ──► 保存/放弃
    │                      │
    │                      否
    │                      ▼
    │               加载计划 B 全量状态
    │
    └─ 新建计划 ──► createEmptyPlan() ──► 全空 UI
```

### 5.3 布局引擎（逻辑图）

初版采用 **时间轴泳道**（§2.6 方案 B），流程：

1. AI 输出带 `day_index`、`order`、`start_time` 的结构化数据  
2. 每个 `day_index` 生成一条泳道（React Flow 子流程或背景分区）  
3. 用 **dagre**（`rankdir: 'LR'`）在泳道内按时间顺序从左到右排列  
4. 备选项节点放在主节点下方，虚线边连接  
5. 用户拖拽后更新 `node.position`，写入 localStorage，下次优先用用户坐标  

保持 **类型配色、实虚线语义、连线标注** 与 `map.png` 一致。

### 5.4 地图与 Geocoding 分工

| 能力 | 实现 | 说明 |
|------|------|------|
| 地图瓦片渲染 | MapLibre + OSM | 免费，仅展示底图 |
| **后端坐标解析** | Geocoding API | `resolve_place` 主来源，**比 web_search 准得多** |
| 编辑时 POI 联想 | 后端 `/geocode/autocomplete` | 仅编辑/确认流，非主界面搜索 |
| 地图点击校准 | 前端地图交互 | 用户手动确认 |
| 路径规划 API | 不做 | 耗时仍由 LLM 推断 |

#### Geocoding API 选型（按目的地）

| 目的地 | 推荐 API | 准确率 | 费用 |
|--------|----------|--------|------|
| **境外（初版）** | **Nominatim / Photon**（OSM） | 知名 POI 高，小店一般 | 免费 |
| 境外（备选） | Mapbox Geocoding / Google Geocoding | 很高 | 有免费额度 |
| **境内（后期）** | **高德 POI 搜索 + 地理编码** | 很高 | 个人有月免费配额 |

**高德是否更准？** — **在国内明显更准**；境外需工单开权限，POI 质量不如专门做全球的 Google/Mapbox，初版境外游建议 **OSM 系 Geocoding 为主、高德为境内扩展**。

#### 修订后的 `resolve_place` 优先级

```
1. Geocoding API（Nominatim/高德）按 name+city 查询  → 主来源
2. Wikidata API（知名地标）                          → 交叉验证
3. web_search + URL/正则                             → 补漏
4. 多源交叉验证 → confidence
5. low/none → 进入 §3.6 用户确认流
```

## 6. 渲染数据契约（核心）

> **本节是前后端与 LLM 的唯一数据契约。**  
> 无论用户输入什么，LLM 必须输出符合此 Schema 的 JSON；前端只负责渲染，不做字段推断。

### 6.1 设计原则

| 原则 | 说明 |
|------|------|
| 固定结构 | 顶层字段不可增减；缺信息用空数组 / 默认值，不可省略必填键 |
| 动态天数 | `days[]` 长度 = 用户行程天数，**无上限** |
| 中文内容 | `title`、`name`、`tips`、`warnings` 等面向用户的字符串均为中文 |
| 坐标内置 | 每个 `node` 必须含 `lat` + `lng`，由 **`resolve_place` + Geocoding API** 填入 |
| 边表驱动 | 路线顺序由 `edges[]` 的 `from → to` 决定，不靠数组顺序猜测 |
| 前端只读业务 | 前端可改 `position`（拖拽坐标）和编辑字段，但不改变 Schema 形状 |

### 6.2 类型定义

```typescript
/** 节点类型枚举 — 前端映射到色块与图标 */
type NodeCategory =
  | 'airport'      // 机场 / 航班
  | 'hotel'        // 酒店
  | 'restaurant'   // 餐厅
  | 'snack'        // 小吃
  | 'attraction'   // 游玩
  | 'landmark'     // 地标 / 枢纽
  | 'transit';     // 交通节点

type EdgeType = 'primary' | 'alternative';

type TransportMode =
  | 'walk' | 'subway' | 'bus' | 'taxi' | 'flight' | 'ferry';

type WeatherIcon =
  | 'sunny' | 'cloudy' | 'overcast' | 'rain' | 'storm' | 'snow';

type CostPer = 'person' | 'total' | 'group';

interface NodeCost {
  amount?: number;
  currency?: string;           // ISO 4217，如 CNY、SGD
  per?: CostPer;
  note?: string;               // 「含门票」「不含餐饮」
}

/** 根对象 — LLM 必须输出的顶层结构 */
interface Itinerary {
  id: string;                  // UUID，后端生成或 LLM 生成均可
  title: string;               // 中文，如「新加坡 4 日游」
  destination: string;         // 中文目的地名
  timezone: string;            // IANA，如「Asia/Singapore」
  days: DayPlan[];             // 长度 = 行程天数，可为 1~∞
  meta: ItineraryMeta;
}

interface ItineraryMeta {
  generated_at: string;        // ISO 8601
  model: string;               // 如「deepseek-v4-pro」
  locale: 'zh-CN';             // 固定中文
  warnings: string[];          // 中文提示，无则 []
}

/** 单日计划 */
interface DayPlan {
  day_index: number;           // 从 1 开始
  date: string;                // YYYY-MM-DD
  weekday: string;             // 中文，如「周三」
  label: string;               // 中文展示名，如「第 1 天 · 抵达樟宜」
  weather?: {
    temp_min: number;
    temp_max: number;
    icon: WeatherIcon;         // sunny | cloudy | overcast | rain | storm | snow
    description: string;       // 中文，如「晴」「多云转阵雨」
    source?: 'llm' | 'manual' | 'api';  // 溯源：生成/手改/API（可选）
  };
  region?: string;             // 可选，当日主区域中文名
  nodes: ItineraryNode[];      // 当日全部节点
  edges: ItineraryEdge[];      // 当日全部连线（含备选）
}

/** 行程节点 — 地图标点 + 路线图节点的唯一数据源 */
interface ItineraryNode {
  id: string;                  // 当日内唯一，如「d1-n3」
  name: string;                // 中文名称
  category: NodeCategory;
  lat: number;                 // WGS84，必填
  lng: number;                 // WGS84，必填
  address?: string;            // 中文地址
  floor?: string;              // 如「L1」「3F」
  start_time?: string;         // HH:mm
  end_time?: string;           // HH:mm
  duration_minutes?: number;   // 停留时长
  is_optional: boolean;        // true → 虚线边框 + 备选语义
  tips?: string[];             // 中文提示；总览模式用 tips[0] 作摘要
  cost_label?: string;         // 展示用开销，如「约 80 元/人」「免费」
  cost?: NodeCost;             // 结构化开销，便于汇总
  region?: string;             // 节点所属区域，总览模式行定位（§3.3.1）
  coord_confidence?: 'high' | 'medium' | 'low' | 'none' | 'manual';
  coord_source?: string;       // 如「wikidata:Q12345」「google_maps_url」
  position?: { x: number; y: number }; // 路线图拖拽坐标，LLM 可不填
}

/** 行程连线 — 路线图箭头 + 地图折线的唯一数据源 */
interface ItineraryEdge {
  id: string;                  // 如「d1-e2」
  from: string;                // 引用 nodes[].id
  to: string;
  type: EdgeType;              // primary=实线, alternative=虚线
  transport_mode: TransportMode;
  duration_minutes: number;    // 路段耗时，LLM 根据搜索推断
  distance_meters?: number;    // 可选，LLM 推断或前端 Turf 计算
  depart_time?: string;        // HH:mm
  arrive_time?: string;        // HH:mm
  label?: string;              // 中文标注，如「地铁 23 分钟」
}
```

### 6.3 字段必填规则

| 对象 | 必填字段 |
|------|----------|
| `Itinerary` | `id, title, destination, timezone, days, meta` |
| `DayPlan` | `day_index, date, weekday, label, nodes, edges` |
| `ItineraryNode` | `id, name, category, lat, lng, is_optional` |
| `ItineraryEdge` | `id, from, to, type, transport_mode, duration_minutes` |

### 6.4 前端渲染映射

| UI 元素 | 数据来源 |
|---------|----------|
| 日期 Tab | `days[].label` 或 `days[].date` |
| 路线图节点 | `days[active].nodes[]` + `position`（有则用之，无则自动布局） |
| 路线图连线 | `days[active].edges[]`，`type` 决定实线/虚线 |
| 地图 Marker | `days[active].nodes[]` 的 `lat/lng/category` |

| 总览节点 | `nodes[]`：类别色块、名称、时间、`cost_label`/`cost`、`tips[0]`、`is_optional` |

## 7. AI Pipeline 设计要点

### 7.1 联网搜坐标：最优解（推荐架构）

**结论：需要 Tool，但不只是「让 LLM 自己搜」——推荐「专用坐标解析 Tool + Agent 循环」。**

#### 为什么不能只靠 Prompt 让 LLM「联网想坐标」

| 方式 | 问题 |
|------|------|
| 单次 Prompt，不开 Tool | LLM 极易**幻觉坐标**；无法追溯来源 |
| 让 LLM 自由调通用搜索 | 搜索结果里坐标格式混乱，LLM 摘录易错 |
| 直接调地图 Geocoding API | ~~冲突~~ → **已采纳为坐标主来源**（后端静默调用，非前端地图搜索） |

#### 三种实现路径对比

| 方案 | 要不要自己写 Tool | 适用场景 | 推荐度 |
|------|-------------------|----------|--------|
| **A. DeepSeek 原生联网** | **不用写搜索逻辑**，但要写 Agent 循环 + 坐标后处理 | 已有 `DEEPSEEK_API_KEY`，想少接第三方 | ⭐⭐⭐ 首选 |
| **B. 自建 `web_search` Tool** | **要写** Tool + 执行循环（Tavily/Serper 等） | OpenAI 兼容端点、需可控搜索源 | ⭐⭐ 备选 |
| **C. 自建 `resolve_place` Tool** | **要写** 一个**专用 Tool**（搜索 + 正则抽坐标） | 对坐标准确率要求高 | ⭐⭐⭐ 与 A/B 组合 |

#### 推荐方案：A + C 组合（两阶段 Agent）

```
用户输入
  │
  ▼
┌─────────────────────────────────────────────────────────┐
│  Phase 1 — 行程规划 Agent（deepseek-v4-pro + 联网）       │
│  Tool: web_search（DeepSeek 原生 或 自建）               │
│  输出: POI 草案列表（名称、类型、时段、tips），暂无坐标    │
└──────────────────────────┬──────────────────────────────┘
                           ▼
┌─────────────────────────────────────────────────────────┐
│  Phase 2 — 坐标解析（每个 POI 并行）                      │
│  Tool: resolve_place(name, city, country)  ← 你要写的    │
│    1. 构造查询: "{name} {city} 经纬度 coordinates"       │
│    2. 调用搜索（复用 web_search）                        │
│    3. 后端正则/规则提取 lat,lng（见下方）                 │
│    4. 返回 { lat, lng, source, confidence }             │
└──────────────────────────┬──────────────────────────────┘
                           ▼
┌─────────────────────────────────────────────────────────┐
│  Phase 3 — 结构化输出（deepseek-v4-pro）                  │
│  输入: POI 草案 + 已解析坐标                              │
│  输出: 严格 Itinerary JSON（§6）                         │
│  校验: Pydantic → 缺坐标写 warnings                       │
└─────────────────────────────────────────────────────────┘
```

**关键设计**：`resolve_place` 是你**必须写**的核心 Tool——把「搜索」和「坐标抽取」封装成确定性后端逻辑，LLM 只负责决定**搜谁**，不负责**猜坐标**。

#### 方案 A：DeepSeek 原生联网（无需第三方搜索 Key）

你 `.env` 已配 `DEEPSEEK_API_BASE=https://api.deepseek.com/v1`（OpenAI 兼容）。  
DeepSeek 的**原生联网搜索**走 **Anthropic 兼容端点**，搜索在服务端执行，**不需要你实现搜索 API 调用**：

| 项目 | 值 |
|------|-----|
| 端点 | `https://api.deepseek.com/anthropic` |
| 模型 | `deepseek-v4-pro`（复杂 Agent 可开 `thinking` + `reasoning_effort: max`） |
| 搜索 Tool | `web_search_20250305` 或 `web_search_20260209`（server-side，DeepSeek 执行） |

注意：OpenAI 兼容端点（`/v1`）**不支持** server-side `web_search`，只有 client-side `tool_calls`。因此：

- **行程规划阶段**：切 Anthropic 端点，挂载 `web_search`，让模型自主搜攻略
- **或**：留在 OpenAI 端点，自建 `web_search` Tool（方案 B）

#### 方案 C：`resolve_place` Tool 定义（建议实现）

```python
# 后端 Tool schema（给 LLM 看）
{
  "name": "resolve_place",
  "description": "根据地点名称解析 WGS84 经纬度，返回可用于地图标点的坐标",
  "parameters": {
    "type": "object",
    "properties": {
      "name": {"type": "string", "description": "POI 中文或官方名称"},
      "city": {"type": "string", "description": "所在城市"},
      "country": {"type": "string", "description": "所在国家"}
    },
    "required": ["name", "city"]
  }
}

# 后端执行逻辑（你不信 LLM 填的数字，只信自己抽的）
async def resolve_place(name: str, city: str, country: str = "") -> dict:
    query = f"{name} {city} {country} 经纬度 latitude longitude coordinates"
    snippets = await web_search(query)          # DeepSeek 原生 or Tavily
    lat, lng = extract_coords(snippets)         # 正则 + 范围校验
    return {
        "lat": lat, "lng": lng,
        "confidence": "high" if lat else "none",
        "source": snippets[0].url if snippets else None
    }
```

`extract_coords` 建议规则：

```python
# 匹配 "1.3644, 103.9915" / "lat: 1.36, lng: 103.99" / "1.3644°N, 103.9915°E"
COORD_PATTERNS = [
    r"(-?\d{1,3}\.\d{3,8})\s*[,，]\s*(-?\d{1,3}\.\d{3,8})",
    r"lat(?:itude)?[:\s]+(-?\d+\.\d+).*?lng|lon(?:gitude)?[:\s]+(-?\d+\.\d+)",
]
# 校验：lat ∈ [-90,90], lng ∈ [-180,180]，且与 destination 大致区域相符
```

#### 阶段划分（落地版）

| 阶段 | 输出 | 工具 / 模型 |
|------|------|-------------|
| 1. 查询改写 | 结构化意图（目的地、天数、偏好） | `deepseek-v4-flash` |
| 2. 行程规划 | POI 列表 + 排程 + tips | `deepseek-v4-pro` + `web_search` |
| 3. 坐标解析 | 每个 POI 的 `lat/lng` | **`resolve_place`（必写）**，可并行 |
| 4. 结构化组装 | 完整 `Itinerary` JSON | `deepseek-v4-pro` + JSON Schema |
| 5. 校验 | 通过 / 修复 / warnings | Pydantic + 规则引擎 |

### 7.5 坐标准确性：web_search 够吗？如何保障？

#### 直说结论

| 问题 | 答案 |
|------|------|
| `web_search` 准确吗？ | **不够**。适合攻略与排程，不适合作为坐标主来源 |
| 借助高德等地图 API 更准吗？ | **是，明显更准**。Geocoding/POI 搜索是坐标解析的**主来源** |
| 能否 100% 保证？ | 自动流程不能；**Geocoding + 分级用户确认**可接近 100% |
| 每次都要二次确认吗？ | **不要**。仅 `medium` 以下或用户主动编辑时确认 |

#### 推荐坐标解析栈（修订）

```
主来源  Geocoding API（境外 Nominatim，境内高德）
辅证    Wikidata（知名地标交叉验证）
补漏    web_search + 地图 URL 解析
兜底    用户确认流（§3.6）：下拉选 / 地图点 / 手输坐标
```

#### web_search 与 Geocoding API 分工

| 职责 | web_search | Geocoding API |
|------|------------|---------------|
| 搜攻略、营业时间 | ✅ 主 | ❌ |
| 排程、生成 tips | ✅ 主 | ❌ |
| **解析 POI 坐标** | ❌ 辅（补漏） | ✅ **主** |
| 同名消歧 | 弱 | **强**（返回结构化地址供用户选） |

#### web_search 不准的常见原因

| 原因 | 示例 |
|------|------|
| 摘要里根本没有坐标 | 攻略只写「松发肉骨茶很好吃」，无 lat/lng |
| 同名 POI | 「中央医院」在不同国家各有一家 |
| 搜到过时/错误坐标 | 博客复制粘贴的旧数据 |
| 正则误匹配 | 把营业时间 `08:30` 或价格当成坐标 |
| LLM 误读摘要 | 把「距机场 1.3 公里」里的数字当坐标 |
| 连锁店 | 搜到品牌坐标，不是具体分店 |

#### 五层保障体系

```
Layer 1  Geocoding API          → 主坐标来源（Nominatim / 高德）
Layer 2  Wikidata 交叉验证       → 知名地标互证
Layer 3  web_search 补漏         → Geocoding 无结果时
Layer 4  规则校验                → bbox、相邻距离
Layer 5  分级用户确认（§3.6）    → 低置信度必须确认；三种校准方式
```

建议：`resolve_place` **优先 Geocoding API**，Wikidata 做交叉验证，web_search 仅作补漏。

---

#### Layer 1：Geocoding API（主来源，替代纯 web_search）

```python
async def geocode_place(name: str, city: str, country: str) -> GeoCandidate | None:
  # 境外
  if is_overseas(country):
      return await nominatim_search(f"{name}, {city}, {country}")
  # 境内（后期）
  return await amap_poi_search(keywords=name, city=city)
```

比 web_search 摘坐标的优势：返回**结构化** `name + address + lat + lng + place_id`，同名 POI 可列出供用户下拉选择。

---

#### Layer 2：结构化辅助与交叉验证

按优先级从搜索结果中提取坐标：

| 优先级 | 来源 | 提取方式 | 可信度 |
|--------|------|----------|--------|
| 1 | Google Maps URL | `@1.3644,103.9915` 或 `!3d1.36!4d103.99` | 高 |
| 2 | OpenStreetMap URL | `#map=17/1.3644/103.9915` 或 `mlat=…&mlon=…` | 高 |
| 3 | Wikipedia 信息框 | 正则 `坐标：1°21′52″N 103°59′29″E` → 转十进制 | 高 |
| 4 | **Wikidata API**（免费） | `wbsearchentities` → `claims.P625` 坐标 | **很高** |
| 5 | 摘要中的十进制坐标 | 正则 `1.3644, 103.9915` | 中 |
| 6 | LLM 从摘要摘录 | 仅当前面都失败时 | 低，需标 `confidence: low` |

**Wikidata 是关键补强**——它不是「地图搜索」，是结构化知识库，免费、有明确实体 ID、坐标准确率高，尤其适合知名景点/地标：

```python
# 免费，无需地图 API Key
# GET https://www.wikidata.org/w/api.php?action=wbsearchentities&search=Marina+Bay+Sands&language=zh
# → 取 entity_id → 再取 P625(coordinate location)
```

建议：`resolve_place` 内部 **先 Wikidata，再 web_search 补漏**，而不是只靠搜索摘要。

#### Layer 3：多源交叉验证

```python
async def resolve_place_verified(name, city, country):
    results = await asyncio.gather(
        wikidata_coords(name, city),       # 结构化
        search_coords(name, city, country), # web_search + URL/正则
    )
    candidates = [r for r in results if r.lat is not None]

    if len(candidates) >= 2:
        dist_m = haversine(candidates[0], candidates[1])
        if dist_m < 500:    # 500m 内 → 互证成功
            return {**candidates[0], "confidence": "high"}
        else:               # 分歧大 → 不自动采纳
            return {"confidence": "conflict", "candidates": candidates}

    if len(candidates) == 1:
        return {**candidates[0], "confidence": "medium"}

    return {"lat": 0, "lng": 0, "confidence": "none"}
```

**规则**：`confidence != high` 的节点写入 `meta.warnings`，前端标点加「?」或橙色边框。

---

#### Layer 4：规则校验

| 规则 | 说明 |
|------|------|
| 范围校验 | `lat ∈ [-90,90]`, `lng ∈ [-180,180]` |
| 目的地包围盒 | 如新加坡约 `lat 1.0~1.5, lng 103.6~104.1`；超出则拒绝 |
| 相邻节点距离 | 同日连续节点不应相距 >500km（除非 `transport_mode=flight`） |
| 类别合理性 | 机场应在城郊；酒店不应在海洋中央 |
| 零坐标拒绝 | `0,0` 视为无效，不渲染到地图 |

包围盒可在 Phase 1 由 LLM 根据目的地生成，或预置常见城市 bbox 表。

---

#### Layer 5：置信度透出 + 用户修正

在 `ItineraryNode` 增加可选字段（或写入 `tips`）：

```typescript
interface ItineraryNode {
  // ...existing fields
  coord_confidence?: 'high' | 'medium' | 'low' | 'none';
  coord_source?: string;   // 如 "wikidata:Q12345" / "google_maps_url"
}
```

前端表现：

| confidence | 地图标点 | 路线图 |
|------------|----------|--------|
| `high` | 正常色块 | 正常 |
| `medium` | 轻微虚线描边 | tips 加「坐标待核实」 |
| `low` / `none` | 橙色 + 「?」| 不连线或虚线到大致区域；`lat/lng=0` 时不落点 |

用户手动编辑 `lat/lng` 后，`coord_confidence` 改为 `manual`（用户确认）。

#### 修订后的 `resolve_place` 流程

```
resolve_place(name, city, country)
  │
  ├─1─► Wikidata API 查实体坐标 ──────────► 有结果 → candidate A
  │
  ├─2─► web_search 多模板
  │       ├─ 解析 Google/OSM URL 坐标 ───► candidate B
  │       └─ 正则摘摘要坐标 ─────────────► candidate C
  │
  ├─3─► 交叉验证 A/B/C → 算 confidence
  │
  ├─4─► 规则校验（bbox、相邻距离）
  │
  └─5─► 返回 { lat, lng, confidence, source }
           confidence < medium → meta.warnings
```

#### 准确率预期（务实估计）

| 方案 | 知名 POI | 小众 POI |
|------|----------|----------|
| 仅 web_search | ~50–60% | 很差 |
| **Geocoding API 为主** | **~90–98%** | ~75–85% |
| + Wikidata 交叉验证 | ~95–99% | ~80–88% |
| + **用户确认流（§3.6）** | **接近 100%** | **接近 100%** |

**结论**：坐标主来源改为 **Geocoding API**；`web_search` 只管内容与排程；消不掉的歧义交给 **分级确认 + 下拉/地图点选**。

### 7.6 输出质量策略

- 坐标**只来自 `resolve_place` 返回值**（§7.5 五层保障），LLM 不得自行编造
- 搜索不到的 POI：`lat/lng = 0,0` + `meta.warnings` 标注，前端显示「待确认」
- `duration_minutes` 由 LLM 根据搜索到的交通信息推断，可二次 `web_search` 查询
- 每个坐标记录 `coord_source` / `coord_confidence`，便于调试与 UI 展示

### 7.7 Prompt 输出约束

- System Prompt 内嵌 **完整 JSON Schema**（§6）与中文输出要求
- 使用 `response_format: json_schema` 或 function calling 强制结构
- 后端 Pydantic 校验 → 不合格触发修复轮次（最多 2 次）
- `days[]` 长度严格匹配用户请求天数，不可擅自增减

### 7.8 技术选型决策

| 决策 | 结论 |
|------|------|
| 是否需要 Tool | **是**：`resolve_place`（必写）+ `web_search`（原生或自建） |
| 搜索 Tool 谁执行 | 优先 DeepSeek 原生 `web_search`（Anthropic 端点）；fallback Tavily |
| 坐标谁说了算 | **Geocoding API 为主** + Wikidata 交叉 + 用户确认兜底 |
| 是否每次二次确认 | **否**；仅低置信度节点或用户编辑时触发 §3.6 |
| Wikidata 角色 | 知名地标交叉验证，非主来源 |
| Agent 框架 | LangGraph / 自写 tool loop；推荐 LangGraph 管理多步状态 |
| 并行策略 | 对所有 POI 并行 `resolve_place`，缩短总耗时 |

## 13. 总结

本项目本质是 **「LLM 联网产出标准 JSON → 路线图 + 地图双 Tab 渲染」**：

1. **看懂**：`map.png` 风格的类型编码、实虚线、耗时标注（路线图 Tab）  
2. **看位置**：MapLibre 标点连线 + 低置信度时地图/下拉校准  
3. **格式统一**：§6 Schema 是 LLM 与前端的唯一契约  
4. **坐得准**：Geocoding API 解析 + 分级用户确认  
5. **改得动**：拖拽编辑 + localStorage，无需登录  
5. **全中文**：界面与生成内容均为中文  

技术栈：**FastAPI + DeepSeek 联网 + React Flow + MapLibre**；前端美学由 **`frontend-design` skill** 约束。

建议下一步：进入 **Phase 0**，用符合 §6 的新加坡 Mock 数据跑通「Tab 切换 + 日期切换 + 双视图联动 + localStorage」。
