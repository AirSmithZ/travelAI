## 一、doc 21 分析

### 1.1 这样做是否更合理？——是，且比 doc 22 更成熟

doc 21 的核心判断经得起推敲，且与代码现状吻合：

- **否决"整包引入 Agent-Reach"**：正确。Agent-Reach 是给桌面 Agent（Cursor/Claude Code）用的"能力安装/路由/体检 CLI"，小红书等渠道依赖 Chrome 会话/Cookie，服务端多租户不友好且有封号风险。文档也如实指出官方建议"用小号"——这说明它本就不该进生产主链。✅
- **否决"另写一套印证系统"**：正确。已证实 `ugc/tikhub.py` 的 `EvidenceItem`（BaseModel，字段 `likes/query/note_id`，行 24–31）、`build_evidence_pack`（行 263）、`evidence_pack.py` 的 `fetch_evidence_pack`/`fetch_evidence_pack_sync` 都已存在，`itinerary_llm.py:327` 的 `_format_evidence_block` 已把证据以"参考公开笔记（印证，非票价）"注入 prompt（上限 12 条，与 doc 21 §7 "混注最多 12 条"一致）。重写零收益。✅
- **"贴切 ≠ 搜更多，而是 检索→结构化→校验→机酒合流"**：这是全篇最有价值的洞察。它把问题从"换更牛的搜索引擎"重新定义为"query 工程 + 过滤 + POI 抽取 + Places 校验 + 硬约束合流"，诊断成熟。✅
- **Phase 0 先 bench 后接线**：数据驱动决策（Tavily/Exa 要不要接），避免感觉驱动。✅
- **诚实边界（§8）与决策清单（§10）**：清晰，且明确"UGC 高赞≠正确/可走""继续禁止摘要入价"。

### 1.2 会修复什么

- **检索质量**：现 `evidence_queries` 只有 `"{dest} 自由行 {n}天"` / `"{dest} itinerary"` 两条（doc 21 §4.2 已点出过粗），扩展为日序/避坑/片区/偏好四槽位，命中更贴。
- **降噪**：软广/串城/单一网红垄断的过滤规则（§4.3）直接提升可行性。
- **可落地收敛**：`extract_poi_candidates → poi_tally → Places 校验`（§4.4–4.5）把"像小红书"变成"坐标真实、类型合理"，是可行性主杠杆。
- **可追溯/信任**：侧栏每条带真实 URL、禁"10w 赞"无出处话术——前提是侧栏真的存在（见下）。

### 1.3 会不会导致什么问题（重点）

🔴 **事实性错误：把"仅 toast"当成"侧栏已具备"。**
doc 21 反复称"已具备 … meta.evidence / **侧栏（WS-04/06/07）**"（§0、§3.2、§4.1.4、§4.4、§4.5、§5、§7、§9），并以此为成功标准（§4.1 #4"侧栏每条有真实 URL"、§9 KPI"侧栏点击"）。但代码事实是：

- 前端**没有** `frontend/src/components/evidence/` 目录，更没有 `EvidencePanel.tsx`（doc 21 §7 明写"已有"——不实）；
- 全局搜 `evidence` 仅命中三处：`types/itinerary.ts:59`（只定义了 `ItineraryEvidenceItem[]` 类型）、`api/itinerary.ts:30`（progress 事件 `step:'evidence'`）、`usePlanStore.ts:586–590`（仅弹一条 toast：`已参考 ${n} 条公开笔记印证（非票价）`）。
- 也就是说，**"侧栏"实际只是一次性 toast，完全没有可点击 URL 的参考面板**。doc 21 围绕"侧栏"写的成功标准、KPI、§7 落点全都建立在不存在的 UI 上——会严重误导排期（以为 UI 已就绪，只需补数据）。

🟠 **WS-08（Places 校验）被定为"可行性主杠杆"，但它尚未启动，且文档未量化新依赖。**
- 后端全仓 grep `ws-08|places_valid|google.*places|fsq|foursquare` **零命中** → WS-08 确为未建。doc 21 把可行性收口押在它身上，但：
  - 已有的 geocode 围栏（GEO-01/02，前几轮已验证）其实已提供"坐标存在 + 落在目的地围栏"的基线校验，文档未说明 WS-08 相对这层基线的增量价值；
  - WS-08 需接入 Google Places / Foursquare 等新 provider，带来**新 API 成本 + 新合规面**，但 §8 风险表只列了 Exa/Agent-Reach，漏了"Places provider 依赖"这一项。

🟠 **POI 抽取与 §8 自相矛盾。** §4.4 新增 `extract_poi_candidates`（小模型或规则+词典）每趟 generate 多一步；但 §8 自己把"检索拖慢 generate"列为风险。文档未给这一步的延迟/成本预算与降级开关，可能亲手制造它警告过的问题。

🟠 **`role` 字段扩展是隐性 schema 变更。** §3.2 提议给 `EvidenceItem` 加 `role:"pattern"|"fact"`，但当前 `EvidenceItem` 无此字段、`_format_evidence_block` 也未用。文档说"可选、勿破坏前端"，却没点明：前端 `ItineraryEvidenceItem` 类型要同步加字段、且分桶逻辑要落到 prompt 拼装——属需协调的契约改动。

🟡 **信任/合规律 disclaimer 无处安放。** §8 要求 UI 文案"公开网页/笔记参考，非平台官方数据"；但既然没有证据面板，这句免责声明没有落点。现 toast 只说"非票价"，**没有"非官方"**，信任风险缓解依赖的 UI 同样不存在。

### 1.4 更好的建议

1. **把"已具备侧栏"改成"仅 toast，需建 EvidencePanel"**，并把 EvidencePanel（URL 列表 + `source` 分组 + 已核验/仅网友提及）列为显式 P1 前端任务，而不是藏在"已具备"里。
2. **WS-08 先对标已完成的 geocode 围栏**写一段"增量价值说明"，并补"Places provider 选型 + 成本 + 合规"到 §8 风险表；建议先复用 geocode 围栏做轻量存在性校验，WS-08 重在做"类型/评分门槛"而非"有没有坐标"。
3. **给 `extract_poi_candidates` 加预算护栏**：并行、TTL 缓存、`timeout` 短、失败跳过，且做成可关的 feature flag（与 §8 自洽）。
4. **`role` 字段**：显式记作 schema 变更，给出 `ItineraryEvidenceItem` 同步改动点。
5. **disclaimer 落到 toast 现成位置**：先在当前 toast 补"非官方数据"五字，别等面板。

## 二、与 doc 22 结论的同步视图

### 2.1 两份文档的分工与关系

| | doc 21 | doc 22 |
|---|---|---|
| 层 | **数据/后端策略**（怎么拿到更贴的玩法证据） | **UX/编排层**（对话怎么呈现进度、校验、玩法） |
| 主交付 | 多 provider EvidencePack、query 工程、POI 抽取、WS-08 校验 | ReadinessChecklist、Activity 进行中气泡、进度可见、单写入路径 |
| 共同主题 | 玩法印证 | 玩法印证 |
| 共同盲区 | **假设 EvidencePanel 侧栏已存在** | **假设 progress 事件前端已渲染进气泡** |

二者互补、无直接冲突（doc 21 喂数据，doc 22 露 UI；都守住"UGC 不覆盖机酒硬约束"）。但——

### 2.2 最关键的结构性发现（同步后最该强调）

**doc 21 与 doc 22 犯了同一种病：都基于"前端渲染层已存在"写需求，而代码里这一层基本是空的。**

- doc 21 的"侧栏" = 一条 toast（无 URL、无面板）；
- doc 22 的"后端缺 progress 事件"前提 = 不成立，后端 `chat_parse.py` / `itinerary_llm.py:528` / `itineraries.py:164` 早就端到端发 `progress`，前端 `api/itinerary.ts:88` 也在消费，只是**喂给了 StatusBar、没进气泡**。

这说明项目处于一种**"后端/数据层跑在前面、前端 UX 层掉队"**的不对称状态，而两份产品文档都不约而同地把缺口算在了"后端没做"，于是给出的解法（doc 21 扩建侧栏数据、doc 22 让 UX-CHAT-06"后端补 evidence progress"）会**修错层或重复造事件**。

### 2.3 doc 22 结论要点（复述，便于一并同步）

- 方向合理、文档卫生变好：`UX-CHAT-*` 已同步进 `docs/TODO-布局与前端.md`（非孤儿待办），修正了前几轮"文档落后代码"的老毛病；同提交还实装了 `manual_validate`/`lodging_search`/`qweather_geo`/SEC-04 白名单测试等后端代码（"本波不实施"仅指 UX 层）。
- **关键误判**：§3b.4 把 Activity 气泡缺口归因为"后端缺 progress 事件"，真实缺口在 UI 不渲染（ChatStatusBar 无 evidence 分支、气泡只显 llmPreview）。照字面做 UX-CHAT-06 会修错层。
- 其它风险：只读摘要卡不减少确认次数（"反复确认"痛点本波不解决）；依赖"前端单一真相源"却没绑 DATA-06；`confirmFlight` 不触发 generate 与 `emptyHint` 承诺错位；移动端未前瞻；`开发进度.md` 未录本次后端特性（轻微漂移）。
- 建议：改写 UX-CHAT-06 为"前端渲染已存在的 progress 事件 + StatusBar 补 evidence 分支"；提前 UX-CHAT-03；UX-CHAT-01 加 DATA-06 前置；confirmFlight 后显式「生成行程玩法」CTA；航班搜活动行是前端活。
