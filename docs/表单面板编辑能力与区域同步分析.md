## 2. 当前编辑模型（实际只有 2.5 种）

### 2.1 选中态与表单映射

```
usePlanStore
├── selectedNodeId  → ItineraryEditor（节点完整表单）
├── selectedEdgeId  → EdgeEditor
└── editorTarget.kind === 'form'
      ├── focus === 'day'    → ItineraryFormEditor · 当日概况
      └── focus === 'region' → ItineraryFormEditor · 区域管理
```

| 编辑入口 | 用户预期 | 现状（P1.5 后） | 表单内容 |
|----------|----------|-----------------|----------|
| **表头 / 当日** | 点总览列头或 Day Tab | ✅ `selectDay` → `ItineraryFormEditor` focus=day | 主题、**日期**、主区域（cascade）、天气 |
| **卡片 / 节点** | 点节点编辑属性 | ✅ `selectNode` | 名称、类型、**RegionCombobox**、时间… |
| **区域轨行** | 点区域名编辑 | ✅ `selectRegion` → focus=region | 区域重命名、新建区域 |

相关文件：

- 表单路由：`frontend/src/components/input/ItineraryEditor.tsx`
- 空态天气：`frontend/src/components/input/DayWeatherEditor.tsx`
- 列头：`frontend/src/components/preview/OverviewGraphView.tsx`（`scrollToDay`）
- 单日 lane-header：`frontend/src/components/graph/ItineraryGraph.tsx`
- 区域解析：`frontend/src/utils/nodeRegion.ts`、`layoutOverview.ts` → `collectRegionsInOrder`

### 2.2 区域在数据层的双层结构

| 字段 | 层级 | 含义 | 谁在用 |
|------|------|------|--------|
| `DayPlan.region` | 日 | 当日**主轴区域**（摘要） | `collectRegionsInOrder` 优先收集；lane-header `day.region ?? day.label` |
| `ItineraryNode.region` | 节点 | 总览矩阵**落格行** | `getNodeRegion` → 单元格分组、拖拽换区 |
| 区域轨 label | **派生** | 全行程区域名去重列表 | `layout.regions`，不可直接持久化 |

解析优先级（已有）：

```text
getNodeRegion(node, day) = node.region → day.region → '其他'
```

**关键（P1.5 后）**：

- 改 **`day.region`（主区域）** → `setDayRegion`：写 `day.region` + **当日**节点有条件 cascade
- 改 **区域轨行名** → `renameRegion`：全行程 batch replace
- 改 **`day.date`** → `setDayDate`：更新 weekday、`trip_request.date_start/end`；列序不一致时 toast（**不重排数组**）

## 3. 补齐「区域编辑」需要改什么（前端）

### 3.1 产品决策（先做选择）

| 方案 | 说明 | 复杂度 |
|------|------|--------|
| **A. 行级重命名** | 点区域轨 → 侧栏编辑「区域名」，批量替换所有 `node.region` / `day.region` 匹配项 | 中 |
| **B. 仅 Day 主区域** | 表头编辑里增加 `day.region`，影响空行占位与默认落格 | 低 |
| **C. 区域实体化** | 引入 `regionId` + 显示名（大改 schema） | 高，本次不荐 |

**建议 Phase 1**：A + B 组合——表头编 Day 概要，区域轨编行级重命名。

### 3.2 Store：扩展选中态

`usePlanStore` 新增（或互斥枚举）：

```typescript
type EditorTarget =
  | { kind: 'node'; id: string }
  | { kind: 'edge'; id: string }
  | { kind: 'day'; dayIndex: number }
  | { kind: 'region'; name: string };  // 区域轨行
```

配套 action：

| Action | 行为 |
|--------|------|
| `selectDay(dayIndex)` | 清 node/edge/region；`setActiveDay`；`leftPanelMode='form'`；总览/地图时 `selectLeftPanelCollapsed` 需展开侧栏 |
| `selectRegion(name)` | 同上，选中区域行 |
| `renameRegion(oldName, newName)` | 遍历 `days[].region` 与 `days[].nodes[].region` 字符串替换；`recordItineraryHistory()` |
| `updateDay(dayIndex, partial)` | **已有**，需暴露 `label` / `region` 表单 |

与现有逻辑协调：

- `selectNode` / `selectEdge` 时清 `editorTarget` 中的 day/region
- 总览/地图折叠侧栏时，点表头/区域轨应 **强制展开**（或提示），否则「编辑表头」不可见

### 3.7 新增区域（与「编辑 / 重命名」不同）

#### 现状

| 能力 | 状态 |
|------|------|
| 节点表单填新 `node.region` | ✅ 自由文本，保存后出现在区域轨 |
| 侧栏「新建区域」入口 | ✅ `RegionEditor` + 区域轨底部「＋ 新建区域」 |
| 无节点空区域行 | ✅ `addRegion` 写 `day.region` 占位 |
| `itinerary.regions[]` 独立字段 | ❌ schema 无（仍为派生） |

区域轨行 = **字符串去重派生**，「新增区域」≠ 插入数据库行，而是让一个新 region 名进入 `collectRegionsInOrder` 结果。

#### 实现策略（前端，推荐分阶段）

| 阶段 | 方案 | 行为 |
|------|------|------|
| **Phase 1** | `addRegion(name, dayIndex)` | 校验重名；将 `days[dayIndex].region = name`（或当前无 `day.region` 的最近一天）；`recordItineraryHistory()`；不强制创建节点 |
| **Phase 1b** | RegionEditor「＋ 新建区域」 | 输入名称 → 调用 `addRegion`；可选「绑定到 Day N」 |
| **Phase 2** | `addRegionWithNode` | 新建区域 + 在该格插入默认节点（复用 `addNode` + `partial.region`） |
| **不推荐** | `itinerary.extra_regions[]` | 需改 schema、patch、compact、导出；仅当必须「全天列空行且无 day.region」时再考虑 |

核心工具（扩写 `regionMutations.ts`）：

```typescript
/** 区域是否已存在于轨中（day.region 或任意 node.region） */
function regionExists(itinerary: Itinerary, name: string): boolean

/** 在指定天写入 day.region，使空区域行出现在总览 */
function addRegionToItinerary(
  itinerary: Itinerary,
  name: string,
  dayIndex: number,
): Itinerary
```

#### UI 入口建议

| 入口 | 动作 |
|------|------|
| 区域轨底部「＋ 新建区域」 | `addRegion` → `selectRegion(name)` |
| `DayEditor` 的 `day.region` | 输入新名即等价于 addRegion（需校验） |
| 总览空单元格右键 / 工具栏 | 「在此区域添加节点」→ `addNode` + region（Phase 2） |

#### 同步影响面

| 模块 | 新增区域后 |
|------|------------|
| `layoutOverview` / 区域轨 | 自动多一行（`regionHeights` 默认空行高） |
| `overviewColumnWidths` | 不变 |
| 地图 | 无节点则无 marker |
| 拖拽换区 | 新名立即出现在 `resolveRegionAtMatrixY` 候选 |
| undo | 需入栈；撤销应恢复 `day.region` 旧值 |

#### 与「重命名区域」关系

- **addRegion**：引入新字符串，通常写 `day.region`
- **renameRegion**：旧名 → 新名，批量替换
- 若 add 的重名应拦截，与 rename 共用 `regionExists`

### 3.8 新增天数

#### 现状

| 能力 | 状态 |
|------|------|
| `addNode(dayIndex)` | ✅ |
| `addDay` / `removeDay` | ✅ `addDay`（末尾追加）；❌ `removeDay`（P2） |
| Patch `action: 'add_day'` | ✅ 类型有；`applyItineraryPatch` 已处理 |
| 对话 add_day | 后端 schema 支持；前端 apply 已补齐 |
| 调整天数 | 手动 `addDay` 同步 `trip_request.day_count`；**未**同步 `date_end` |

#### 日期推算：现状与问题（2026-06-30 复核）

**当前实现**（`itineraryMutations.createDefaultDay`）：

```typescript
// 未传 options.date 时
dateAfter(firstDay.date, insertIndex)   // insertIndex = 即将插入的下标
```

| 场景 | insertIndex | 推算结果 | 是否正确 |
|------|-------------|----------|----------|
| 末尾追加 4→5 天，各日日期连续 | `4` | `days[0].date + 4 天` | ✅ 与「末日起 +1 天」一致 |
| 末尾追加，但中间某日日期被改过 / LLM 产出有间隔 | `4` | 仍按 `days[0]+4` | ❌ 可能与 **已有某日同日期** 或 **早于末日的日期** |
| 未来中间插入（P2） | `i` | `days[0]+i` | ❌ 未考虑前后邻日，几乎必冲突 |

**根因**：用 **数组下标** 当 **日历偏移**，默认各 `day.date` 严格等于 `days[0]+(i-1)`。一旦真实日期链断裂，新增天就会**撞日**或**倒序**。

**示例（冲突）**：

```text
Day1  2026-10-16
Day2  2026-10-17
Day3  2026-10-20   ← 中间跳了两天（生成或将来手改）
Day4  2026-10-21
追加 Day5：算法 → 2026-10-16 + 4 = 2026-10-20  ← 与 Day3 重复
```

**DayEditor 日期**：`date` / `weekday` 仅只读展示（`day-editor__meta`），**不可选、不可改**。

**与 `trip_request` 关系**：

| 字段 | addDay 后 | 说明 |
|------|-----------|------|
| `day_count` | ✅ 同步为 `days.length` | 已实现 |
| `date_start` | 不变 | 仍应对齐 `days[0].date`（未自动校验） |
| `date_end` | ❌ 未更新 | 末日出游结束日可能滞后 |

#### 默认 Day 结构

新建一天至少包含：


| 字段 | 规则 | P1 实现 | 建议（P1.5） |
|------|------|---------|--------------|
| `day_index` | 插入后全表 **1..N 重排** | ✅ | — |
| `date` / `weekday` | 见 §11 | ⚠️ 首日+索引 | **末日起 +1** + 冲突检测；DayEditor 可选日期 |
| `label` | `第 N 天` 或带目的地 | ✅ | — |
| `region` | 继承 `days[i-1].region` | ✅ | — |
| `nodes` / `edges` | `[]` | ✅ | — |
| `weather` | 默认 cloudy 22–30°C | ✅ | — |

## 10. 区域同步语义与节点区域控件（2026-06-30 增补）

> 针对：**(1) 表头改主区域要不要同步节点？(2) 节点区域要不要改下拉？**

### 10.1 表头「主区域」与节点 `node.region` 是否应同步

#### 先区分两条编辑路径

| 入口 | UI 字段 | Store / 工具 | 写入范围 | 是否同步 node |
|------|---------|--------------|----------|---------------|
| 列头 / Day Tab → DayEditor | **主区域** | `updateDay(dayIndex, { region })` | 仅 `days[i].region` | ❌ **否** |
| 区域轨 → RegionEditor | **区域名称** | `renameRegion(old, new)` → `renameRegionInItinerary` | 全行程所有 `day.region` / `node.region` 字符串匹配项 | ✅ **是** |

代码依据：

- `DayEditor.tsx`：`onChange` 直接 `updateDay`，无 cascade
- `regionMutations.renameRegionInItinerary`：遍历全部 `days[].region` 与 `days[].nodes[].region` 做 replace

#### 改 `day.region` 后，各节点实际落格（`getNodeRegion`）

```text
getNodeRegion(node, day) = node.region ?? day.region ?? '其他'
```

| 节点数据状态 | 改 `day.region`（A→B）后总览落格 | 用户主观感受 |
|--------------|----------------------------------|--------------|
| `node.region` 为空 / 未设 | 随 `day.region` 落到 **B** 行 | 「同步了」 |
| `node.region === A`（曾显式写入或与旧主区域一致） | 仍落 **A** 行 | 「没同步 / 改表头没用」 |
| `node.region === C`（其它区域） | 仍落 **C** 行 | 符合预期 |

**典型踩坑**：生成或 geocode 后若跑过 `ensureDayNodeRegions`，节点往往已有**显式** `node.region`，此时再改 DayEditor 主区域，矩阵里节点**不会跟着动**，但 `day.region` 与区域轨占位可能已变，出现「主区域写了 B，节点还在 A 行」的分裂。

#### 结论：要不要同步？

| 场景 | 是否应同步节点 | 理由 |
|------|----------------|------|
| 用户想**重命名区域轨上的一行**（如「牛车水」→「牛车水商圈」） | ✅ 应全局同步 | 已有 **RegionEditor**，不要用 DayEditor 代替 |
| 用户想改**当日摘要 / 默认落格**（Day 主轴区域） | ⚠️ **仅建议同步当日、有条件** | 全行程 batch 会误伤其它天的同名区域 |
| 用户只想改**新加节点的默认值** | ❌ 不必同步已有节点 | 当前 `createDefaultNode` 已读 `day.region` |

**产品建议（P1.5）**：

1. **保持两条入口语义分离**  
   - **改行名、跨天批量** → 点区域轨 → `RegionEditor` / `renameRegion`  
   - **改当日主区域** → DayEditor；**不要**把 `updateDay({ region })` 做成全局 rename

2. **DayEditor 增加「当日有条件 cascade」（推荐默认开启或二次确认）**  
   当 `oldDayRegion → newDayRegion` 时，对 **同一 `dayIndex`** 下节点：

   ```text
   若 !node.region?.trim()  OR  node.region === oldDayRegion
     → node.region = newDayRegion
   否则不动
   ```

   配套工具（拟新增）：

   ```typescript
   syncDayRegionToNodes(itinerary, dayIndex, oldRegion, newRegion): Itinerary
   countDayNodesAffected(itinerary, dayIndex, oldRegion): number
   ```

   UI：若 `count > 0`，改值前提示「将同步更新当日 N 个节点的落格区域」。

3. **不建议**：DayEditor 改主区域时无差别替换**全行程**所有 `node.region === old`（那是 `renameRegion` 的职责，易与「只改这一天」混淆）。

#### 同步影响面（若实现 P1.5 cascade）

| 模块 | 行为 |
|------|------|
| 总览矩阵 | 当日受影响节点换行；`layoutOverview` 自动重算 |
| 区域轨 | 若旧名无其它引用可能少一行；新名可能出现 |
| undo | 与 `updateDay` 同一 history 条目，或拆成 compound op |
| RegionEditor rename | 逻辑不变，仍是全局 replace |

### 10.2 节点表单「区域」是否应改为下拉

#### 现状

`ItineraryEditor.tsx` 中节点 **区域** 为 `FormInput` 自由文本，`placeholder = day.region`；可选清空以继承当日主区域（`node.region` undefined → fallback `day.region`）。

候选区域列表来源（已有）：

```typescript
collectRegionsInOrder(itinerary.days)
// 顺序：各天 day.region（按天序）→ 各 node 落格区域去重
```

#### 纯下拉（`<select>` 仅列已有区域）的利弊

| 优点 | 缺点 |
|------|------|
| 避免错别字导致多出一行空区域轨 | **无法**直接输入行程里尚未出现的新区域名 |
| 与总览行标签一致 | 必须先走区域轨「新建」或 DayEditor，路径变长 |
| 降低认知负担 | 同一天多子区域（如「滨海湾 · 金沙酒店内」）不友好 |

#### 结论与建议

**推荐 Combobox（可搜索下拉 + 可自定义），不是纯下拉。**

| 控件形态 | 建议 |
|----------|------|
| 主控件 | `FormSelect` 或带 `datalist` 的 input（可复用 **场景分组** 同一模式） |
| 选项 | `collectRegionsInOrder` 全量区域 + **「继承当日主区域」**（value 空，展示 `day.region ?? 其他`） |
| 自定义 | 保留「其它…」项或允许输入 list 外新字符串（新建区域仍走 `addRegion` 或直接写 `node.region`） |
| 默认值 | 新节点：`createDefaultNode` 已用 `day.region`；表单打开时对空 region 显示 inherit 态 |

**不推荐**纯只读下拉的原因：区域在本产品里是**派生字符串**而非封闭枚举；节点级落格常需要比「已有列表」多一个细粒度名称，纯 select 会把用户堵在表单外。

#### 拟实现要点（P1.5）

| 文件 | 改动 |
|------|------|
| `ItineraryEditor.tsx` | 区域字段 → Combobox；`useMemo` 拉 `collectRegionsInOrder` |
| 可选 `RegionCombobox.tsx` | 封装 options + inherit + custom |
| `utils/regionMutations.ts` | 可选 `listAllRegions(itinerary)` 薄封装 |

## 11. 新增天数：日期顺延与可选编辑（2026-06-30 增补）

> 针对：**追加的天是否应自动往后延且不撞日？Day 日期是否应支持用户选择？**

### 11.1 结论摘要

| 问题 | 结论 |
|------|------|
| 新增天日期要不要自动往后延？ | **要**；应用 **上一自然日 +1 天**（或 `max(已有 date)+1`），**不要**仅用 `days[0].date + insertIndex` |
| 要不要避免与已有天冲突？ | **要**；候选日与已有 `day.date` 重复时继续 +1，直到唯一 |
| 日期要不要支持选择？ | **要**；DayEditor 增加日期控件（`<input type="date">` 或共用 DateField）；`weekday` **只读派生**，不手填 |
| 节点上的「时间」？ | 已有 `TimePicker`（`start_time` / `end_time`）；本节 **Day 级日历日期**，不是节点时刻 |

### 11.2 推荐推算规则（P1.5）

#### 末尾追加（当前唯一支持的路径）

```typescript
function nextAvailableDate(existingDates: string[], afterDate: string): string {
  const used = new Set(existingDates);
  let cursor = afterDate;
  do {
    cursor = addCalendarDays(cursor, 1);
  } while (used.has(cursor));
  return cursor;
}

// append 时
const last = itinerary.days.at(-1);
const anchor = last?.date ?? trip_request.date_start ?? todayLocal();
const date = nextAvailableDate(allDayDates(itinerary), anchor);
const weekday = weekdayFromDate(date);
```

| 优先级 | 锚点 | 说明 |
|--------|------|------|
| 1 | `days[last].date + 1` | 符合「行程往后延长」直觉 |
| 2 | `trip_request.date_start` | 尚无 day 时 |
| 3 | 本地今天 | 兜底 |

**冲突处理**：若 `+1` 仍落在已有某天的 `date` 上（用户曾手改、跳日），循环 +1 直到不重复。

#### 中间插入（P2，预埋）

| 策略 | 行为 |
|------|------|
| **默认** | `days[i-1].date + 1`；若 ≥ `days[i].date` 则提示「将顺延后续日期」 |
| **Ripple** | 可选：从插入点起后续每天 +1，保持相对间隔（复杂，P2 再定） |

### 11.3 DayEditor：日期可选

| 项 | 建议 |
|----|------|
| 控件 | `FormDateInput`（`form-date-wrap` + `color-scheme: dark` + 自定义日历 affordance） |
| 变更 | `updateDay(dayIndex, { date, weekday })`；`weekday` 由 util 计算 |
| 校验 | 软提示：与其它 `day.date` 重复时 toast「与其它天同日，请确认」；**不硬拦**（允许同日多 Day 的极端场景） |
| 展示 | 列头 / DayTabs 继续读 `day.date`、`day.weekday`，改后自动刷新 |

**注意时区**：现有 `dateAfter` 用 `toISOString().slice(0,10)`，在部分时区可能 **UTC 偏移 ±1 天**。P1.5 应改为 **本地年月日** 格式化（见 §11.4 工具）。

## 12. 行程公共表单与按日期重排（2026-06-30 增补）

> 针对：**(1) 区域编辑并入 DayEditor，并升格为「公共表单数据编辑器」？(2) 把某天的日期改到其它天之前，是否会整体迁移该天数据？**

### 12.1 DayEditor → 行程公共表单编辑器

#### 现状：两套侧栏、两种语义

| 组件 | 触发 | 编辑对象 | 作用域 |
|------|------|----------|--------|
| `DayEditor` | 列头 / Day Tab / lane-header | `DayPlan`：label、主区域、天气 | **单日** `days[i]` |
| `RegionEditor` | 区域轨 | 区域名字符串 | **全行程** batch rename / 新建 |
| `ItineraryEditor`（节点） | 点节点 | `ItineraryNode` | 单节点 |
| `EdgeEditor` | 点连线 | `ItineraryEdge` | 单条边 |

用户体感：「改行程公共信息」要在 **Day 表单** 与 **区域表单** 间切换，且区域轨与表头职责重叠（§10 已述 `day.region` vs `renameRegion` 不同步问题）。

#### 产品方向（建议采纳）

将 `DayEditor` **重命名并升格**为 **行程公共表单编辑器**（代码名建议：`ItineraryFormEditor`），定位为：

> **除节点 / 连线外的行程级、可编辑公共字段的统一容器**  
> （Day 概况、区域管理、日期、天气、追加天等；未来可扩展行程备注、预算摘要等。）

**不是**取消「Day / 区域」两种数据语义，而是 **合并 UI 壳层**，用同一组件 + 不同 **focus** 呈现。

#### 推荐结构

```text
ItineraryFormEditor（原 DayEditor）
├── focus === 'day'    → 当日概况区块（默认）
│     label / date / day.region / 天气 / 末尾追加天
├── focus === 'region' → 区域管理区块（原 RegionEditor）
│     区域重命名（renameRegion）/ 引用节点数 / ＋ 新建区域
└── 可选：公共顶栏 Tab「当日 · 区域」切换 focus
```

| 入口 | editorTarget（拟） | 表单表现 |
|------|-------------------|----------|
| 列头 / Day Tab | `{ kind: 'form'; focus: 'day'; dayIndex }` | 当日概况为主；可折叠「本日涉及区域」快捷链到 region |
| 区域轨 | `{ kind: 'form'; focus: 'region'; regionName }` | 区域管理为主；列出「落在该区域的天」只读 |
| 无选中（fallback） | `{ kind: 'form'; focus: 'day'; dayIndex: activeDayIndex }` | 与现空态一致 |

**Store**：`editorTarget.kind === 'region'` 可 Deprecated，统一为 `'form'` + `focus`；`selectRegion(name)` 改为 `selectForm({ focus:'region', regionName })`。

#### 区域编辑「放进公共表单」的具体分工

| 字段 / 操作 | 放在哪 | 行为 | 与 §10 关系 |
|-------------|--------|------|-------------|
| **主区域** `day.region` | 当日概况 | 仅写当日；可选 **当日节点有条件 cascade** | §10.1 P1.5 |
| **区域重命名** | 区域管理 | `renameRegion`，全行程 replace | 原 RegionEditor |
| **＋ 新建区域** | 区域管理 | `addRegion` | 可从表单或区域轨入口 |
| 节点落格 `node.region` | 仍在 **节点表单** | Combobox | §10.2 |

**关键**：合并 UI **不等于**合并语义——表单里要用 **区块标题 + 说明文案** 区分「当日主区域」与「重命名行程中的区域行」，避免用户以为改主区域等于改区域轨。

#### 迁移步骤（P1.5）

| 步骤 | 内容 |
|------|------|
| 1 | `DayEditor.tsx` → `ItineraryFormEditor.tsx`；吸收 `RegionEditor` 区块 |
| 2 | `ItineraryEditor` 去掉 `RegionEditor` 分支；统一渲染 `ItineraryFormEditor` |
| 3 | `InputPanel` 标题：`编辑 · Day N` / `编辑 · 区域 · XX` 按 focus 保留 |
| 4 | 删除或 re-export `RegionEditor` 为内部子组件 `FormRegionSection` |
| 5 | 区域轨点击仍展开侧栏，仅改路由到 `focus:'region'` |

#### 验收（拟增）

| # | 场景 | 期望 |
|---|------|------|
| V20 | 点列头 | 公共表单 · 当日概况，无 Region 独立页 |
| V21 | 点区域轨 | 同一公共表单 · 区域管理区块高亮 |
| V22 | 改「主区域」vs「区域重命名」 | 文案区分；后者仍全局 batch |

### 12.2 修改日期：是否按日期整体迁移 Day 槽位？

#### 现状：**不会**自动迁移

行程天的 **权威顺序** 是 `itinerary.days[]` **数组下标**，不是 `day.date` 字典序：

| 概念 | 绑定 | 说明 |
|------|------|------|
| 总览列序 / Day Tab 顺序 | `days[0..n-1]` | 第 3 列 = 数组 index 2 |
| `day_index` 显示 | `i + 1` | 随数组重排而变 |
| `activeDayIndex` | 数组下标 | 切 Tab 改下标 |
| 节点 id 前缀 | `d{dayIndex+1}-n*` | 与 **当前槽位** 绑定，非日历 |
| `cross_day_edges` | 相邻 **数组槽位** 的末/首节点 | 不按 date 计算 |

因此：在 DayEditor 把 **Day5 的 `date` 改成比 Day3 更早**，**当前只会改字段**：

```text
改前：days[4].date = 10-21  （界面仍是第 5 列 / Day 5）
改后：days[4].date = 10-18  （仍在 index 4，但日历早于 days[2]）
```

**不会**发生：

- ❌ 把 Day5 的 nodes/edges/weather 整体挪到 index 2
- ❌ 总览列、Tab、DayChips 按日期重排
- ❌ `day_index` / node id / 跨日边自动跟着日历走

#### 用户问题：「是不是应该整体往前迁移？」

| 策略 | 说明 | 建议 |
|------|------|------|
| **A. 只改 date，不重排数组** | 实现简单；「Day N」= 行程第 N 天，**不一定**等于日历第 N 天 | 仅作过渡；需 UI 提示日期与列序不一致 |
| **B. 改 date 后自动按日期排序数组** | 用户改 Day5→10-18 后，若早于 Day3，**整包** `DayPlan`（nodes/edges/weather/label/region）插入正确下标 | **推荐作为可选行为**，默认需确认 |
| **C. 显式「按日期排序行程」按钮** | 用户主动触发 `sortDaysByDate()`，一次性重排 | 与 B 二选一或并存 |

**若采用 B/C「整体迁移」**，一次 reorder 必须动的是 **整个 `DayPlan` 对象**（当日全部节点与边），并附带：

| 连带项 | 是否必须 | 说明 |
|--------|----------|------|
| `days[]` splice / 插入 | ✅ | 槽位迁移本体 |
| 重算 `day_index` | ✅ | 1..N |
| `cross_day_edges` | ✅ | 按新相邻天重建或 `migrateCrossDayEdges` |
| `overviewColumnWidths[]` | ✅ | 列宽数组随列序 permute |
| `activeDayIndex` / `editorTarget.dayIndex` | ✅ | 跟踪被编辑天的新下标 |
| **node id 前缀 `dN`** | ⚠️ P2 决策 | 重排后 id 与 day_index 错位；要么 **migrateNodeIds**，要么文档接受脱钩 |
| 区域轨 / 矩阵 | 自动 | 数据随 days 变而重算 |

**不应**只迁移 nodes 不迁移 edges，或只改 date 不移动数组元素——否则 Day 内拓扑与跨日边会断裂。

#### 推荐产品规则（P2）— 已落地

1. **默认**：改日期 **仅** `setDayDate`；破坏单调性时 toast + 表单内 **「按日期排序」** 按钮。
2. **显式重排**：`sortDaysByDate()` → `reorderItineraryDaysByDate`（方案 C，无改 date 后弹窗）。
3. **排序 tie-break**：`date` 相同则保持原相对顺序（稳定排序）。
4. **连带**：`migrateItineraryNodeIds` + `rebuildCrossDayEdges` + `overviewColumnWidths` permute + `activeDayIndex` / `editorTarget` 跟踪。

#### 拟 API

```typescript
/** 按 day.date 稳定排序 days[]，返回新 itinerary + oldIndex→newIndex 映射 */
function reorderItineraryDaysByDate(itinerary: Itinerary): {
  itinerary: Itinerary;
  indexMap: Map<number, number>;
}

/** 将单一 day 从 fromIndex 移到 toIndex（整体搬 DayPlan） */
function moveDayInItinerary(
  itinerary: Itinerary,
  fromIndex: number,
  toIndex: number,
): Itinerary
```

`moveDayInItinerary` 可用于拖拽 Tab 排序；`reorderItineraryDaysByDate` 用于「按日历对齐列序」。

#### 验收（拟增）

| # | 场景 | 期望 |
|---|------|------|
| V23 | 仅改 Day5 日期到 Day3 前（不重排） | 数据仍在第 5 槽；列序不变；有 inconsistency 提示 + 排序按钮 |
| V24 | 点击「按日期排序」 | Day5 整包移到 Day3 前；nodes/edges 完整；列头/Tabs 顺序=日期序 |
| V25 | 排序后 undo | 恢复数组序、date、cross_day_edges |
| V26 | 在此天后插入 | 新 Day 插入正确槽位；后续 day_index / node id 重编 |
| V27 | 删除非空 Day | confirm 后删除；至少保留 1 天 |
| V28 | 总览列头有节点 | 副行显示 `N 站 · Xmin` |
